# Участие в разработке

Сообщения об ошибках и предложения можно оставить в [issues адаптера](https://github.com/ShadobaAI/kafka-adapter/issues).

## Задачи проекта { #issue-tracking }

Задачи разработки ведутся в [kfk-tasks](https://github.com/ShadobaAI/kfk-tasks/issues), ход работ отражается на [доске GitHub Projects](https://github.com/users/ShadobaAI/projects/3/views/1).

## Сообщить об ошибке { #report-bug }

Укажите версию адаптера, платформы и БСП, вид установки, ожидаемый и фактический результат. Приложите шаги воспроизведения и относящиеся к сбою фрагменты журнала. [Где искать журнал](../user/operations/diagnostics.md)

## Предложить улучшение { #propose-change }

Опишите задачу, ожидаемое поведение и затронутые сценарии. Значимые изменения стоит обсудить в issue до реализации. Изменения публичного API, схемы данных и нетривиальные изменения поведения оформляются по правилам рабочего пространства.

## Прислать pull request { #pull-request }

1. Опишите цель и затронутые компоненты. Для новых объектов соблюдайте префиксы и правила репозитория-владельца. [Репозитории](repositories.md)
2. В начале нового файла `*.bsl` добавьте заголовок лицензии MPL 2.0. Проверка из корня адаптера: `python3 .github/scripts/check_bsl_license.py`.
3. Приведите релевантные проверки для кода, очередей или форм. Если менялись интерфейсы или пользовательское поведение, обновите соответствующую страницу документации. [Тестирование](repositories.md#testing)

Для изменений схемы очереди проверьте права и формы, запросы фоновых процессов, очистку, внешнее логирование и обновление обеих форм поставки. Для изменений фоновой обработки проверьте статусы после сбоя, перезапуска и ручного возврата. Для изменений API проверьте существующих вызывающих, значения по умолчанию и жизненный цикл сессий.
