# Описание AsyncAPI

AsyncAPI — спецификация для описания API систем, которые обмениваются сообщениями. Документ AsyncAPI задаёт контракт обмена: каналы, направления передачи сообщений и структуру их данных. Он помогает отправителям и получателям согласовать формат обмена, служит основой для документации и проверки сообщений, а также может использоваться инструментами генерации схем и кода.

В YAML эти сведения представлены как разделы и свойства. Для обмена через Kafka каналы описывают топики, операции — отправку и получение, а схемы — структуру JSON-тел сообщений.

Описанный формат включает метаданные контракта, каналы, операции, сообщения и схемы данных. Настройки подключения к брокеру, безопасность, заголовки сообщений и ключ Kafka находятся за пределами этого описания.

## Имена и направление обмена

Для каждого вида сообщения в документе используются пять имён:

| Имя | Где используется | Пример |
| --- | --- | --- |
| Адрес топика | `channels.<канал>.address` | `crm.order.changed` |
| Идентификатор канала | Ключ в `channels` и ссылка из операции | `orderChanged` |
| Идентификатор операции | Ключ в `operations` | `sendOrder` |
| Идентификатор сообщения | Ключ в `components.messages`, значение его `name` | `OrderMessage` |
| Локальное имя сообщения канала | Ключ в `channels.<канал>.messages` и ссылка из операции | `order` |

Дополнительно используется имя схемы тела сообщения, например `Order`, в `components.schemas`. Эти имена могут различаться: адрес нужен для доставки, остальные — для связей внутри описания.

Имена всех элементов контракта подчиняются единой договорённости. Например, адреса топиков можно записывать как `crm.<тип>.changed`, сообщения — как `<Тип>Message`, схемы — как `<Тип>`, операции — как `send<Тип>` или `receive<Тип>`. Конкретный канал может иметь собственные имена. В документе записываются окончательные имена; ссылки используют те же значения.

Направление определяется с точки зрения приложения, которому принадлежит спецификация:

- `send` — приложение отправляет сообщение.
- `receive` — приложение получает сообщение.

В описываемом контракте каждому каналу соответствует одно сообщение и одна операция. Описание содержит действующие маршруты обмена. Определения схем могут присутствовать и без использования каналами, например как библиотека общих типов.

## Расширения `x-*`

Свойства с префиксом `x-` являются расширениями AsyncAPI. Они дополняют стандартную структуру документа сведениями, специфичными для проекта или инструментов обработки. `x-*` обозначает группу имён; буквальный ключ `x-*` в YAML не используется.

Имя расширения начинается с `x-`, например `x-last-modified`, `x-enumNames` или `x-topics`. Значение может быть строкой, числом, логическим значением, списком или объектом. Его структура и смысл определяются договорённостью проекта. Расширение располагается в том объекте, к которому относится, если этот объект допускает расширения.

Расширения позволяют хранить дополнительные метаданные без изменения смысла стандартных свойств. Они не заменяют `type`, `required`, `enum`, `$ref` и другие средства описания контракта. Например, список подписей `x-enumNames` поясняет значения перечисления, но допустимые значения по-прежнему задаются через `enum`.

Пример расширения с объектным значением:

```yaml
x-last-modified:
  at: '2026-09-15T10:00:00'
  name: 'Иван Петров'
  email: 'ivan@example.com'
```

Здесь `x-last-modified` содержит сведения о последнем изменении документа. Вложенные `at`, `name` и `email` являются свойствами самого расширения; префикс `x-` для них не требуется. Это пример проектных метаданных, а не стандартный обязательный раздел AsyncAPI. Его наличие в описываемом профиле определяется договорённостью о составе документа.

Поддержка расширений зависит от инструмента: неизвестное свойство `x-...` может сохраняться в документе, но не влиять на обработку. Само наличие расширения не означает, что валидатор проверяет его внутренние поля или что скрипт использует их при генерации. Если расширение влияет на результат обработки, его расположение, тип значения, обязательность и поведение при отсутствии задаются отдельными требованиями к соответствующему инструменту.

## Метаданные документа

```yaml
asyncapi: '3.1.0'

info:
  title: 'Обмен заказами CRM'
  version: '1.0.0'

x-last-modified:
  at: '2026-09-15T10:00:00'
  name: 'Иван Петров'
  email: 'ivan@example.com'

defaultContentType: application/json
```

| Свойство | Что записывать и зачем |
| --- | --- |
| `asyncapi` | Строку `'3.1.0'`: версия формата документа. |
| `info.title` | Читаемое название спецификации. |
| `info.version` | Строку с версией контракта обмена. Она изменяется независимо от версии формата AsyncAPI. |
| `x-last-modified.at` | Дату последнего изменения строкой в формате даты-времени. |
| `x-last-modified.name` | Имя автора последнего изменения. |
| `x-last-modified.email` | Почту автора; при отсутствии адреса ключ пропускается. |
| `defaultContentType` | `application/json`: общий тип содержимого тела сообщений. |

`x-last-modified` — пользовательское расширение для истории изменений. Оно не является настройкой обмена и не определяет состав JSON.

## Каналы

```yaml
channels:
  orderChanged:
    title: 'Изменение заказа'
    address: crm.order.changed
    messages:
      order:
        $ref: '#/components/messages/OrderMessage'
```

`channels` — словарь каналов. `orderChanged` — внутренний идентификатор; `title` — название для читателя; `address` — фактический адрес топика Kafka.

`messages` внутри канала — словарь, а не список. Ключ `order` обозначает сообщение именно в этом канале. Его `$ref` указывает на общее определение сообщения. Это связывает маршрут доставки с форматом сообщения без копирования определения.

## Операции

```yaml
operations:
  sendOrder:
    action: send
    channel:
      $ref: '#/channels/orderChanged'
    messages:
      - $ref: '#/channels/orderChanged/messages/order'
```

`operations` — словарь действий приложения. `action` содержит `send` или `receive`. `channel` ссылается на канал.

`messages` операции — список ссылок. В этом профиле он содержит один элемент. Ссылка ведёт на локальное сообщение выбранного канала, а не непосредственно на `components.messages`: так операция однозначно выбирает сообщение в своём маршруте.

Получению соответствует `action: receive` и имя операции, например `receiveOrder`. Адрес канала от выбора направления автоматически не меняется.

## Сообщения и схемы данных

```yaml
components:
  messages:
    OrderMessage:
      name: OrderMessage
      payload:
        $ref: '#/components/schemas/Order'
  schemas:
    Order:
      title: 'Заказ'
      type: object
      properties:
        id:
          type: string
          format: uuid
        number:
          type: string
      required:
        - id
        - number
```

`components.messages` хранит определения сообщений. `name` повторяет идентификатор сообщения. `payload` ссылается на схему его JSON-тела.

`components.schemas` хранит схемы типов данных и перечислений. Верхнеуровневые типы получают имена схем; вложенные свойства называются кодами полей. Вложенные структуры описываются внутри `properties`, а не автоматически выносятся в отдельные компоненты.

Полная цепочка связей:

```text
operations.sendOrder.channel → channels.orderChanged
operations.sendOrder.messages[0] → channels.orderChanged.messages.order
channels.orderChanged.messages.order → components.messages.OrderMessage
components.messages.OrderMessage.payload → components.schemas.Order
```

## Типы и свойства схем

Свойствам `type` и `format` соответствуют следующие значения:

| Данные | `type` | Дополнительное описание |
| --- | --- | --- |
| Текст | `string` | Ограничения длины и регулярное выражение при необходимости. |
| Число с дробной частью | `number` | Нижняя и верхняя границы при необходимости. |
| Целое число | `integer` | Значение по умолчанию при необходимости. |
| Логическое значение | `boolean` | `true` или `false`, без кавычек. |
| Структура | `object` | Поля в `properties`, обязательные поля в `required`. |
| Массив | `array` | Схема одного элемента в `items`. |
| UUID | `string` | `format: uuid`. |
| Дата и время | `string` | `format: date-time`. |
| Дата | `string` | `format: date`. |
| Время | `string` | `format: time`. |

Форматы UUID и дат также описаны в [описании генерации XSD из YAML](xsd-generation.md). `format` уточняет базовый тип; UUID остаётся строкой.

Общие свойства схемы и любого вложенного поля:

| Свойство | Когда добавлять | Назначение |
| --- | --- | --- |
| `title` | Есть читаемое название | Краткая подпись типа или поля. |
| `description` | Есть описание | Смысл, правила заполнения и пояснения для пользователя. |
| `deprecated: true` | Тип или поле устарело | Обозначает необходимость перехода на замену; для действующего поля ключ можно пропустить. |
| `type` | Тип описывается непосредственно | Вид значения JSON. |
| `format` | Задан уточняющий формат | Например, UUID или дата-время. |
| `$ref` | Используется перечисление или переиспользуемый тип | Ссылка на существующую схему. |

### Структура и обязательность

```yaml
type: object
properties:
  number:
    type: string
  comment:
    type: string
required:
  - number
```

`required` размещается у структуры и содержит имена её обязательных непосредственных свойств. Ключ `required: true` у отдельного поля не используется. При отсутствии обязательных полей `required` отсутствует.

Обязательность означает присутствие свойства. Она сама по себе не задаёт минимальную длину строки и не разрешает `null`. В этом профиле не используются `nullable`, тип `null` и запрет дополнительных свойств через `additionalProperties: false`.

### Массив

```yaml
type: array
minItems: 1
maxItems: 100
items:
  type: object
  properties:
    quantity:
      type: number
      minimum: 0
  required:
    - quantity
```

`minItems` и `maxItems` ограничивают количество элементов. `items` описывает каждый элемент непосредственно, без промежуточного ключа с именем элемента. Он может содержать примитив, структуру или `$ref`.

`items` содержит одну однозначную схему элемента. Обязательное присутствие массива задаётся в `required` родителя, а непустота — через `minItems`.

### Строка

```yaml
type: string
minLength: 1
maxLength: 20
pattern: '^[A-Z0-9-]+$'
default: 'NEW'
```

`minLength` и `maxLength` ограничивают длину; `pattern` — допустимое содержимое; `default` — значение по умолчанию. Незаданные ограничения отсутствуют. Служебные значения вроде `-1` не обозначают отсутствие границы в YAML.

### Число и значение по умолчанию

```yaml
type: number
minimum: 0
maximum: 1000000
default: 0
```

`minimum` и `maximum` задают включительные границы числового значения. В описываемом профиле они используются для `number`. Для целого числа базовое описание состоит из `type: integer` и, при необходимости, `default`.

`default` используется для строк, чисел, целых чисел и логических значений. Значение записывается явно с соответствующим типом: строка в кавычках, число и логическое значение без кавычек. Ноль, `false` и пустая строка — самостоятельные значения; их можно указать явно, если они предусмотрены контрактом.

## Перечисления

```yaml
components:
  schemas:
    OrderStatus:
      type: string
      enum:
        - 'new'
        - 'confirmed'
      x-enumNames:
        - 'Новый'
        - 'Подтверждён'
    Order:
      type: object
      properties:
        status:
          $ref: '#/components/schemas/OrderStatus'
```

`enum` — список допустимых значений, которые передаются в JSON. `x-enumNames` — рекомендуемое необязательное расширение для расшифровки элементов перечисления. Оно содержит параллельный список читаемых представлений: позиции двух списков должны соответствовать друг другу. Представления не заменяют значения обмена.

**Наименование перечисления** является ключом схемы и окончанием `$ref`. Описание содержит действующие перечисления. При наличии читаемых представлений `x-enumNames` содержит подпись для каждого элемента.

Поле с перечислением содержит `$ref` на его схему. Тип и допустимые значения определяются в схеме перечисления; все использующие её поля имеют одинаковые требования. Самостоятельные `type`, `format`, ограничения и `default` у такого поля в этом профиле не указываются.

## Переиспользование и составные типы

Если тип полностью переиспользует другой тип и не добавляет собственных полей, он описывается ссылкой:

```yaml
Customer:
  $ref: '#/components/schemas/Party'
```

Если базовых типов несколько, используется `allOf`: значение должно удовлетворять всем перечисленным схемам одновременно. Это объединение требований, а не выбор одного варианта.

Собственные поля представлены отдельным элементом списка:

```yaml
ExtendedOrder:
  allOf:
    - $ref: '#/components/schemas/OrderIdentity'
    - $ref: '#/components/schemas/OrderDetails'
    - type: object
      properties:
        comment:
          type: string
```

Такую форму массива схем подтверждает [раздел Composition and Inheritance AsyncAPI 3.1.0](https://www.asyncapi.com/docs/reference/specification/v3.1.0#schemaObject).

Каждая ссылка и каждое описание собственных полей должны быть самостоятельным элементом списка `allOf`, начинающимся с `-`. Свойства этого элемента, включая `type`, `properties`, `required` и `default`, располагаются внутри него с одинаковым уровнем отступа.

## Связанные объекты и UUID

```yaml
customerId:
  title: 'Покупатель'
  type: string
  format: uuid
  x-topics:
    - crm.customer.changed
    - crm.partner.changed
```

`x-topics` — рекомендуемое необязательное расширение для описания связи UUID-поля с топиками типов объектов, на которые оно может ссылаться. Это практика документирования связей между объектами обмена, а не обязательное требование AsyncAPI. Это список адресов топиков, а не `$ref` и не список идентификаторов каналов. Значение поля в JSON остаётся UUID; структура связанного объекта в него не вкладывается.

Расширение применяется к строковым UUID-полям с известными связанными типами объектов и содержит фактические адреса топиков этих типов. Обычное UUID-поле без установленной связи с типами объектов может не иметь `x-topics`.

## Синтаксис YAML

- Вложенные уровни имеют отступы по два пробела.
- Словари представлены как `ключ: значение`, списки — строками с `-`.
- Значения `$ref` заключены в кавычки: незакавыченный `#` начинает комментарий.
- Строки, похожие на числа, даты или логические значения, заключаются в кавычки для сохранения текстового типа. Особенно это важно для версий и строковых значений `enum` и `default`.
- В одинарных кавычках апостроф удваивается: `'Заказ клиента O''Brien'`.
- Многострочное описание можно оформить через `|-` с более глубоким отступом строк текста.
- Ключи внутри одного словаря уникальны. Имена каналов, операций, сообщений, типов и перечислений должны исключать коллизии в своих разделах.
- Простые внутренние ссылки используют имена без `/` и `~`; такие имена не требуют специального экранирования в путях `$ref`.

```yaml
description: |-
  Данные заказа после изменения.
  Номер обязателен для идентификации в CRM.
```

Версии, дата изменения, ссылки и однострочные описания представлены в кавычках. Кавычки также сохраняют тип и содержимое названий, регулярных выражений, значений перечислений и других текстов.

## Пример документа

Пример описывает отправку заказа из CRM. Имена и бизнес-поля иллюстрируют структуру контракта.

```yaml
asyncapi: '3.1.0'

info:
  title: 'Обмен заказами CRM'
  version: '1.0.0'

x-last-modified:
  at: '2026-09-15T10:00:00'
  name: 'Иван Петров'
  email: 'ivan@example.com'

defaultContentType: application/json

channels:
  orderChanged:
    title: 'Изменение заказа'
    address: crm.order.changed
    messages:
      order:
        $ref: '#/components/messages/OrderMessage'

operations:
  sendOrder:
    action: send
    channel:
      $ref: '#/channels/orderChanged'
    messages:
      - $ref: '#/channels/orderChanged/messages/order'

components:
  messages:
    OrderMessage:
      name: OrderMessage
      payload:
        $ref: '#/components/schemas/Order'
  schemas:
    Order:
      title: 'Заказ'
      description: 'Данные заказа после изменения'
      type: object
      properties:
        id:
          title: 'Идентификатор'
          type: string
          format: uuid
        number:
          title: 'Номер'
          type: string
          minLength: 1
          maxLength: 20
        createdAt:
          type: string
          format: date-time
        status:
          $ref: '#/components/schemas/OrderStatus'
        customerId:
          type: string
          format: uuid
          x-topics:
            - crm.customer.changed
        lines:
          title: 'Товары'
          type: array
          minItems: 1
          items:
            type: object
            properties:
              productId:
                type: string
                format: uuid
                x-topics:
                  - crm.product.changed
              quantity:
                type: number
                minimum: 0
            required:
              - productId
              - quantity
      required:
        - id
        - number
        - lines
    OrderStatus:
      type: string
      enum:
        - 'new'
        - 'confirmed'
      x-enumNames:
        - 'Новый'
        - 'Подтверждён'
```

Пример JSON-тела, соответствующего приведённому описанию:

```json
{
  "id": "12e2cfc6-aefd-463f-a87f-0f328834ca41",
  "number": "ORD-001",
  "status": "new",
  "lines": [
    {
      "productId": "ce3020a7-edbf-4397-bd7f-e53c49744894",
      "quantity": 2
    }
  ]
}
```

Требования к входному YAML для преобразования описаны отдельно в разделе [Требования к YAML для генерации XDTO-модели](yaml-requirements-for-xdto.md). Поддержка свойства в AsyncAPI сама по себе не означает его поддержку существующим скриптом генерации.

## Справочник ключей и свойств

В этом разделе тип «словарь» означает набор именованных ключей YAML, а тип «список» — последовательность элементов с `-`. Угловые скобки в путях обозначают выбранное автором имя и в файл не записываются.

### `asyncapi`

- **Расположение:** корень документа.
- **Тип:** строка; значение этого профиля — `'3.1.0'`.
- **Обязательность:** обязательное свойство.
- **Назначение:** определяет, по какой версии структуры AsyncAPI инструмент должен читать документ.
- **Почему так:** версии AsyncAPI различаются структурой описания каналов и операций. Этот документ использует отдельный раздел `operations`, соответствующий версии 3.
- **Пример:** `asyncapi: '3.1.0'`. Версия продукта или контракта относится к `info.version`.

### `info`

- **Расположение:** корень документа.
- **Тип:** словарь с `title` и `version`.
- **Обязательность:** обязательный раздел.
- **Назначение:** объединяет сведения о контракте, которые не являются полями сообщения.
- **Почему так:** название и версия относятся ко всему API, поэтому записываются один раз, отдельно от каналов и JSON-схем.

### `title`

- **Расположение:** `info.title`, `channels.<канал>.title`, схема или поле схемы.
- **Тип:** строка.
- **Обязательность:** в `info` обязательно; у канала в описываемом профиле задаётся название; у схем и полей можно пропустить при отсутствии подписи.
- **Назначение:** короткое название для читателя: «Обмен заказами», «Изменение заказа», «Идентификатор покупателя».
- **Почему так:** технический ключ нужен для ссылок, а подпись — для понимания. Изменение подписи не требует переименования ключа.
- **Ограничение:** `title` не является адресом топика, именем JSON-поля или идентификатором схемы.

### `version`

- **Расположение:** `info.version`.
- **Тип:** строка.
- **Обязательность:** обязательное свойство `info`.
- **Назначение:** версия описанного контракта, например `'1.0.0'`.
- **Почему так:** формат документа и бизнес-контракт развиваются независимо. Для изменения состава полей меняется версия контракта, а не обязательно `asyncapi`.
- **Оформление:** кавычки сохраняют текстовый тип значения.

### `x-last-modified`

- **Расположение:** корень документа.
- **Тип:** словарь с `at`, `name` и необязательным `email`.
- **Обязательность:** присутствует в описываемом профиле.
- **Назначение:** сведения о последнем изменении описания.
- **Почему так:** префикс `x-` отделяет пользовательские метаданные от стандартных свойств AsyncAPI. Сведения об изменении не смешиваются с бизнес-полями JSON.

### `at`

- **Расположение:** `x-last-modified.at`.
- **Тип:** строка даты-времени, например `'2026-09-15T10:00:00'`.
- **Назначение:** момент последнего изменения документа.
- **Оформление:** между датой и временем используется `T`; кавычки сохраняют значение строкой. Если указан часовой пояс, он должен соответствовать реальному моменту изменения.
- **Ограничение:** это не время создания каждого сообщения. Время бизнес-события описывается отдельным полем `payload`.

### `name`

- **Расположение:** `x-last-modified.name` и `components.messages.<сообщение>.name`.
- **Тип:** строка.
- **Назначение:** в метаданных — имя автора; в сообщении — имя сообщения, совпадающее с его ключом в `components.messages`.
- **Почему так:** одинаковый ключ имеет смысл в контексте своего объекта. Имя автора и имя сообщения не связаны между собой.
- **Примеры:** `name: 'Иван Петров'` и `name: OrderMessage`.

### `email`

- **Расположение:** `x-last-modified.email`.
- **Тип:** строка с адресом электронной почты.
- **Обязательность:** необязательное свойство; при отсутствии адреса ключ отсутствует.
- **Назначение:** контакт автора изменения для вопросов по контракту.
- **Ограничение:** адрес не используется для маршрутизации сообщений и не является учётной записью брокера.

### `defaultContentType`

- **Расположение:** корень документа.
- **Тип:** строка; значение — `application/json`.
- **Назначение:** сообщает, что тела сообщений по умолчанию передаются в JSON.
- **Почему так:** все сообщения используют общий формат сериализации, поэтому он задаётся один раз.
- **Ограничение:** это описание формата, а не команда преобразования данных. Фактически отправленное тело также должно быть JSON и соответствовать схеме.

### `channels`

- **Расположение:** корень документа.
- **Тип:** словарь; каждый ключ — идентификатор канала.
- **Обязательность:** нужен при описании маршрутов обмена; при их отсутствии раздел можно пропустить.
- **Содержимое канала:** `title`, `address`, `messages`.
- **Назначение:** перечисляет маршруты, которые использует приложение.
- **Почему так:** маршрут существует независимо от действия приложения; направление задаётся отдельно в операции.

### `address`

- **Расположение:** `channels.<канал>.address`.
- **Тип:** строка с адресом топика Kafka.
- **Назначение:** фактическое место отправки или получения сообщения.
- **Почему так:** ключ `orderChanged` удобен как идентификатор документа, а `crm.order.changed` соответствует инфраструктуре обмена.
- **Ограничение:** значение является адресом топика, а не адресом брокера или путём `#/channels/...`.

### `messages`

- **Расположение и тип:** в канале — словарь локальных сообщений; в операции — список ссылок на сообщения канала; в `components` — словарь определений сообщений.
- **Назначение:** связывает доступное на маршруте сообщение, выбор операции и переиспользуемое определение его тела.
- **Почему так:** эти три контекста отвечают на разные вопросы: что доступно в канале, что передаёт операция и как описано сообщение.
- **Обязательность:** каждый маршрут этого профиля представлен во всех трёх контекстах.
- **Типичная ошибка:** запись `messages` операции как словаря вместо списка или ссылка из операции прямо на компонент сообщения.

### `operations`

- **Расположение:** корень документа.
- **Тип:** словарь; каждый ключ — уникальный идентификатор операции.
- **Содержимое операции:** `action`, `channel`, `messages`.
- **Назначение:** описывает действия приложения в каналах.
- **Почему так:** одно и то же понятие канала может использоваться для отправки или получения; действие нельзя выводить только из имени топика.
- **Обязательность:** нужен при описании действий обмена; без маршрутов раздел можно пропустить.

### `action`

- **Расположение:** `operations.<операция>.action`.
- **Тип:** строка с одним из значений `send`, `receive`.
- **Обязательность:** обязательное свойство операции.
- **Назначение:** направление действия относительно описываемого приложения.
- **Почему так:** отправитель и получатель имеют разные контракты поведения даже при одинаковом формате JSON.
- **Ограничение:** `publish`, `subscribe`, «отправка» и «получение» не являются значениями этого свойства.

### `channel`

- **Расположение:** `operations.<операция>.channel`.
- **Тип:** объект ссылки с `$ref`.
- **Обязательность:** обязательное свойство операции.
- **Назначение:** выбирает канал, в котором выполняется действие.
- **Пример:** `$ref: '#/channels/orderChanged'` внутри `channel`.
- **Почему так:** повторное описание адреса в операции создало бы две независимые копии одного маршрута.

### `$ref`

- **Тип:** строка внутри объекта ссылки.
- **Назначение:** переиспользует определение по указанному пути.
- **Пути этого профиля:** канал — `#/channels/<канал>`; сообщение канала — `#/channels/<канал>/messages/<локальное-имя>`; сообщение-компонент — `#/components/messages/<сообщение>`; схема — `#/components/schemas/<схема>`.
- **Почему так:** формат тела и перечисления описываются один раз, а места использования ссылаются на них.
- **Оформление:** путь заключён в кавычки; целевой ключ должен существовать и совпадать по регистру.
- **Ограничение:** ссылка на схему описывает тип значения. Она не означает, что в JSON вместо значения передаётся строка с путём `$ref`.

### `components`

- **Расположение:** корень документа.
- **Тип:** словарь с разделами `messages` и `schemas`.
- **Назначение:** хранит общие определения для ссылок.
- **Почему так:** отделяет библиотеку типов и сообщений от маршрутов и действий приложения.
- **Использование:** компонент может применяться в нескольких местах; само объявление схемы не создаёт канал или операцию.

### `payload`

- **Расположение:** `components.messages.<сообщение>.payload`.
- **Тип:** в этом профиле — объект ссылки на схему.
- **Назначение:** определяет структуру JSON-тела сообщения.
- **Пример:** `$ref: '#/components/schemas/Order'` внутри `payload`.
- **Почему так:** сообщение описывает единицу обмена, а схема описывает её данные и может переиспользоваться.
- **Ограничение:** `payload` не добавляет одноимённую оболочку в JSON. При схеме `Order` отправляется сам объект заказа.

### `schemas`

- **Расположение:** `components.schemas`.
- **Тип:** словарь именованных схем.
- **Назначение:** описывает типы тел сообщений, общие типы и перечисления.
- **Содержимое:** схема может быть непосредственным описанием типа, ссылкой `$ref` или составной конструкцией `allOf`.
- **Почему так:** требования к данным отделяются от способов доставки.
- **Ограничение:** имя схемы не становится JSON-полем; поля объекта определяются в `properties`.

### `description`

- **Расположение:** схема или свойство схемы.
- **Тип:** строка, включая многострочный блок `|-`.
- **Обязательность:** необязательное свойство.
- **Назначение:** объясняет смысл данных, единицы измерения, договорённости заполнения и причины ограничений.
- **Почему так:** `type: number` не сообщает, например, что количество измеряется в штуках.
- **Ограничение:** словесное требование само по себе не заменяет машинное ограничение. Непустота строки выражается дополнительным свойством `minLength: 1`.

### `deprecated`

- **Расположение:** схема или свойство схемы.
- **Тип:** логическое значение; для устаревшего элемента — `true` без кавычек.
- **Обязательность:** указывается при устаревании; иначе можно пропустить.
- **Назначение:** обозначает элемент, от использования которого следует переходить к замене.
- **Почему так:** позволяет сохранить совместимость и одновременно сообщить о миграции.
- **Ограничение:** не удаляет поле и не отменяет его обязательность. Замена и порядок перехода описываются в `description`.

### `type`

- **Расположение:** схема, свойство в `properties` или схема `items`.
- **Тип:** строка: `string`, `number`, `integer`, `boolean`, `object`, `array`.
- **Назначение:** задаёт базовый вид JSON-значения.
- **Почему так:** одинаковое текстовое представление может иметь разный смысл: `"2"` — строка, `2` — число.
- **Использование:** непосредственное описание содержит явный тип. При ссылке тип определяется целевой схемой.
- **Ограничение:** названия 1С вроде «Строка» или «Структура» не являются значениями `type`.

### `format`

- **Расположение:** рядом с `type` в схеме.
- **Тип:** строка, например `uuid`, `date-time`, `date`, `time`.
- **Обязательность:** необязательное уточнение.
- **Назначение:** сообщает семантику значения внутри базового типа.
- **Почему так:** UUID и дата — текстовые значения с определённой формой, поэтому описываются как `string` с уточнением.
- **Ограничение:** `format` не заменяет `type`; запись `type: uuid` неверна. Проверка конкретного формата зависит от возможностей используемого инструмента.

### `properties`

- **Расположение:** схема с `type: object`.
- **Тип:** словарь; каждый ключ совпадает с именем поля JSON.
- **Назначение:** описывает допустимые типы и ограничения каждого именованного свойства.
- **Почему так:** вложенность YAML отражает вложенность объекта данных.
- **Обязательность:** используется для описания полей структуры.
- **Ограничение:** наличие поля в `properties` не делает его обязательным; для этого нужен `required` родителя.

### `required`

- **Расположение:** рядом с `properties` у соответствующего объекта.
- **Тип:** список строк — имён непосредственных полей.
- **Назначение:** требует присутствия перечисленных свойств.
- **Почему так:** обязательность является требованием к составу объекта, а не отдельным типом поля.
- **Использование:** имена должны совпадать с ключами `properties`; вложенный объект имеет собственный список.
- **Ограничение:** не означает непустую строку, непустой массив или разрешённый `null`. При отсутствии обязательных полей список можно не задавать.

### `items`

- **Расположение:** схема с `type: array`.
- **Тип:** одна схема элемента массива, непосредственная или ссылочная.
- **Назначение:** задаёт форму каждого элемента.
- **Почему так:** у массива есть собственные ограничения количества, а у элемента — отдельные требования к данным.
- **Обязательность:** присутствует у описываемого массива.
- **Ограничение:** между `items` и `type` отсутствует промежуточное имя вроде `row`: схема элемента описана непосредственно.

### `minItems` и `maxItems`

- **Расположение:** у массива рядом с `type` и `items`.
- **Тип:** неотрицательное целое число; каждое свойство необязательно.
- **Назначение:** `minItems` задаёт минимальное, `maxItems` — максимальное количество элементов.
- **Почему так:** ограничение количества относится ко всему массиву, а не к отдельной строке.
- **Проверка:** при наличии обеих границ `minItems` не должен превышать `maxItems`.
- **Примеры:** `minItems: 1` требует непустой массив; `maxItems: 100` допускает не более ста элементов. Отсутствующий массив этим не запрещается — для присутствия нужен `required` родителя.

### `minLength` и `maxLength`

- **Расположение:** у поля или схемы `type: string`.
- **Тип:** неотрицательное целое число; каждое свойство необязательно.
- **Назначение:** `minLength` задаёт минимальную, `maxLength` — максимальную длину строки в символах.
- **Почему так:** ограничения длины описывают допустимое содержимое независимо от обязательности поля.
- **Проверка:** нижняя граница не должна превышать верхнюю. Фиксированной длине соответствуют одинаковые значения обеих границ.
- **Пример:** `minLength: 1`, `maxLength: 20`. Наличие только верхней границы допускает пустую строку.

### `pattern`

- **Расположение:** у схемы `type: string`.
- **Тип:** строка с регулярным выражением.
- **Назначение:** ограничивает форму текста, например допустимые символы номера.
- **Почему так:** длина не определяет набор символов или порядок частей значения.
- **Пример:** `pattern: '^[A-Z0-9-]+$'`. Якоря `^` и `$` явно требуют соответствия всей строки.
- **Оформление:** одинарные кавычки удобны для выражений с обратными косыми чертами, поскольку сохраняют их буквально.

### `minimum` и `maximum`

- **Расположение:** у числовой схемы; в этом профиле — `type: number`.
- **Тип:** число без кавычек; каждое свойство необязательно.
- **Назначение:** `minimum` задаёт нижнюю, `maximum` — верхнюю включительную границу.
- **Почему так:** допустимый диапазон является свойством значения, а не текстового представления числа.
- **Проверка:** нижняя граница не должна превышать верхнюю.
- **Пример:** при `minimum: 0` допустимы `0` и положительные числа. Дробная часть отделяется точкой, например `maximum: 99.5`.

### `default`

- **Расположение:** рядом с типом соответствующего поля или схемы.
- **Тип:** значение того же типа, что описано схемой.
- **Обязательность:** необязательное свойство.
- **Назначение:** фиксирует согласованное значение по умолчанию.
- **Почему так:** потребителям контракта нужна единая договорённость о значении, когда отдельное значение не задано.
- **Примеры:** для строки `default: 'NEW'`, числа `default: 0`, логического поля `default: false`.
- **Ограничение:** свойство не делает поле обязательным и само по себе не гарантирует автоматическую вставку значения отправителем, получателем или валидатором. Значение должно удовлетворять ограничениям своей схемы.

### `enum`

- **Расположение:** схема перечисления в `components.schemas`.
- **Тип:** список допустимых значений базового типа схемы.
- **Назначение:** задаёт закрытый набор значений обмена.
- **Почему так:** статус должен передаваться согласованным кодом, а не произвольным текстом.
- **Использование:** список непустой и содержит различные значения. Строковые коды заключены в кавычки; числовые коды представлены числами.
- **Ограничение:** читаемая подпись из `x-enumNames` не становится допустимым значением, если её нет в `enum`.

### `x-enumNames`

- **Расположение:** рядом с `enum` в схеме перечисления.
- **Тип:** список строк.
- **Обязательность:** необязательное; рекомендуется для расшифровки элементов перечисления.
- **Назначение:** содержит расшифровку каждого значения `enum` в виде читаемой подписи.
- **Почему так:** коды удобны для обмена, а подписи — для документации и интерфейсов.
- **Проверка:** количество элементов и порядок должны совпадать с `enum`. Для `enum: ['new', 'confirmed']` подписи идут как `['Новый', 'Подтверждён']`.
- **Ограничение:** обработка расширения зависит от инструмента; допустимость значений определяет `enum`.

### `allOf`

- **Расположение:** схема в `components.schemas` или вложенная схема.
- **Тип:** список схем, в том числе объектов с `$ref`.
- **Назначение:** требует одновременного выполнения всех входящих описаний.
- **Почему так:** позволяет составить тип из нескольких общих наборов свойств и собственных дополнений.
- **Оформление:** каждая схема начинается с `-`; собственные `type`, `properties` и `required` входят в отдельный элемент списка.
- **Ограничение:** несовместимые требования не превращаются в варианты. Если одна схема требует строку, а другая число для того же значения, объединённое требование невыполнимо.

### `x-topics`

- **Расположение:** строковое поле с `format: uuid`.
- **Тип:** список строк — адресов топиков связанных типов объектов.
- **Обязательность:** необязательное; рекомендуется как практика документирования при известной связи UUID с объектами обмена.
- **Назначение:** поясняет, где публикуются объекты, идентификаторы которых допустимы в поле.
- **Почему так:** один формат UUID не раскрывает, относится ли ссылка к покупателю, товару или нескольким типам объектов.
- **Пример:** `x-topics: [crm.customer.changed, crm.partner.changed]`.
- **Ограничение:** не создаёт подписку, не загружает связанный объект и не заменяет значение UUID. Это метаданные контракта, а не встроенное правило проверки существования объекта.
