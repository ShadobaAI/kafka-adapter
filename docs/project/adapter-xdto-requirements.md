# Поддерживаемая модель XDTO в Адаптере Kafka

Адаптер Kafka использует **Конвертацию данных 3.1** для преобразования данных объектов метаданных 1С в XDTO-модель обмена и обратного преобразования полученных данных в данные конфигурации. Модуль `кфкОбменДаннымиXDTOСервер` создан копированием стандартного модуля 1С `ОбменДаннымиXDTOСервер` с последующими доработками для адаптера. Поддержка EnterpriseData унаследована от стандартного механизма; доработки позволяют также использовать собственный XDTO-формат, построенный по подобию EnterpriseData.

Этот раздел описывает поддерживаемую модель: типы объектов и значений, ссылки, ключевые свойства, таблицы, составные свойства и соглашения, необходимые для работы конвертации. Общие понятия механизма приведены в разделе [XDTO](xdto.md), настройки обмена — в разделе [Конвертация данных 3.1](../user/development/conversion-data.md).

## Метаданные, модель формата и правила

Метаданные конфигурации описывают справочники, документы, регистры, реквизиты и табличные части. XDTO-модель задаёт представление их данных для обмена. КД 3.1 связывает эти описания правилами; обмен не сводится к автоматической записи любого объекта конфигурации в JSON.

| Данные 1С | Представление в модели обмена |
| --- | --- |
| Элемент справочника, документ или другая сущность | Объектный тип формата. |
| Реквизит | Свойство объектного типа. |
| Строка, число, дата или логическое значение | Тип значения XDTO. |
| Перечисление конфигурации | Согласованное значение перечисления формата. |
| Ссылка на объект | Ссылочное значение либо ключевые свойства согласно правилам. |
| Табличная часть | Табличный объект с коллекцией строк. |
| Строка табличной части как единица обмена | Самостоятельный объект формата. |
| Запись регистра | Объект данных записи; несколько записей могут образовывать пакет. |

Имена метаданных и имена формата могут различаться. ПКС определяют, например, что реквизит `Количество` заполняет свойство `quantity`, а ссылка `Номенклатура` — идентификатор товара. Собственные алгоритмы правил могут вычислять значения и изменять представление данных.

### Состав правил

| Правило | Назначение |
| --- | --- |
| ПОД — правило обработки данных | Выбирает обработку источника и используемые ПКО. |
| ПКО — правило конвертации объекта | Связывает данные конфигурации с типом объекта формата. |
| ПКС — правило конвертации свойства | Связывает реквизит или вычисленное значение со свойством формата. |
| Правила табличных частей | Сопоставляют таблицы, строки и их свойства. |
| Правила конвертации предопределённых данных | Задают соответствие значений, в частности перечислений, при отправке и получении. |

Модуль обмена содержит эти правила и их обработчики. Готовый XDTO-пакет без согласованных правил не определяет поиск объектов, заполнение реквизитов и запись данных в информационную базу.

## Форматы и область требований

- [EnterpriseData: унаследованная поддержка](#enterprisedata-унаследованная-поддержка) — стандартный пакет, ссылки на основе `Ref`, ключевые свойства и стандартные типы таблиц.
- [Произвольный формат](#произвольный-формат) — собственный контракт, назначение и состав модели, UUID, идентификация и самостоятельные строки.
- [Общие требования конвертации](#общие-требования-конвертации) — доступность типов, представление сообщения, обработка значений и коллекций, обязательность, `null` и проверка модели.

## EnterpriseData: унаследованная поддержка

EnterpriseData описывает бизнес-сущности независимо от внутренней схемы конкретной информационной базы. Например, документы и элементы справочников представлены типами формата, а правила конфигурации задают преобразование их данных. Назначение формата изложено в [официальном описании EnterpriseData](https://v8.1c.ru/tekhnologii/obmen-dannymi-i-integratsiya/standarty-i-formaty/format-enterprisedata/).

Адаптер распознаёт стандартный формат по началу пространства имён `http://v8.1c.ru/edi/edi_stnd/EnterpriseData/` без учёта регистра. Пример версии 1.25: `http://v8.1c.ru/edi/edi_stnd/EnterpriseData/1.25`.

Возможность работы с EnterpriseData сохраняет логику стандартного модуля 1С, включая специальную обработку ключевых свойств и ссылки объекта. Это унаследованная возможность конвертации, а не отдельная разработанная в адаптере реализация стандарта EnterpriseData. Пакет и правила должны соответствовать используемой версии модели. Происхождение модуля и сохранение этой ветки обработки не означают взаимозаменяемость всех версий EnterpriseData, наличие каждого пакета в любой конфигурации или автоматическую совместимость со всеми последующими изменениями стандартного модуля 1С.

### Ссылки EnterpriseData на основе `Ref`

В стандартном EnterpriseData ссылки представлены простыми типами, являющимися потомками `Ref` из пространства имён `http://www.1c.ru/SSL/Exchange/Message`. Это механизм ссылок EnterpriseData; ссылки собственного формата `tns:UUID` описаны в отдельном разделе о произвольном формате.

В EnterpriseData 1.25 тип `ТипСсылкаОбъектная` имеет базу `Ref`, а конкретные типы вроде `ДокументСсылка.АвансовыйОтчет` уточняют ссылку на бизнес-сущность. Стандартные ссылки не обязаны иметь имя `UUID`.

| Представление | Назначение |
| --- | --- |
| Тип на базе `Ref` | Ссылочное значение стандартной модели EnterpriseData. |
| Объект ключевых свойств | Данные сопоставления сущности, включая ссылку и другие поля. |
| Полный объект формата | Данные сущности, а не только её идентификатор. |
| Обычная строка | Текст без автоматической ссылочной семантики. |

При чтении ссылки EnterpriseData адаптер сохраняет её тип и значение во внутреннем представлении для конвертации. Восстановление ссылки 1С зависит от ПКО, типа объекта и способа идентификации, а не только от строкового представления ссылки.

### Ключевые свойства и ссылка объекта

Для стандартного EnterpriseData адаптер отдельно учитывает блок `КлючевыеСвойства`. Он определяет тип ключевого объекта, отмечает соответствующие ПКС и получает тип свойства `Ссылка`. При чтении ссылка из блока также поднимается в структуру данных для правил объекта.

Например, в EnterpriseData 1.25 тип `КлючевыеСвойстваАвансовыйОтчет` содержит дату, номер, организацию, ссылку и внешнюю навигационную ссылку. Состав ключей других сущностей отличается. Ключевые свойства — не обязательно только UUID и не универсальный одинаковый набор полей.

### Пример структуры EnterpriseData

```text
Документ.АвансовыйОтчет
  → ВыданныеАвансы
    → Документ.АвансовыйОтчет.ВыданныеАвансы
      → Строка[]
        → Документ.АвансовыйОтчет.ВыданныеАвансы.Строка
```

Тип строки содержит собственные свойства. При отправке из таблицы данных формируются объекты этих строк; при получении восстанавливается таблица значений с колонками по модели строки.

Стандартные типы таблиц используют общий механизм табличных объектов, описанный ниже. Имена и состав типов определяются выбранной версией EnterpriseData.

## Произвольный формат

Поддержка собственного формата расширяет унаследованный механизм обмена XDTO и КД 3.1. Доработки адаптера сохраняют общий принцип правил преобразования, но позволяют применять его к собственной модели вместо обязательного использования стандартных сущностей EnterpriseData.

Произвольный формат использует собственное пространство имён, типы и состав данных. Он сохраняет общую организацию: сущность — объект формата, реквизиты — свойства, таблица — коллекция строк, ссылка — идентификатор, варианты составного значения — согласованное объектное представление.

Например, контракт может описывать тип `Order` с полями `id`, `number` и `lines`. Соответствие этих полей метаданным определяется ПКС. В произвольном формате ссылочные поля используют собственный тип `tns:UUID`.

Подобие EnterpriseData не требует копировать все его бизнес-сущности, стандартные имена и блоки. Однако форма таблиц, соглашения об объектных свойствах и правила идентификации должны соответствовать механизмам адаптера. Произвольный формат означает собственный контракт в рамках этой модели, а не поддержку любой возможной XSD без дополнительных правил.

Собственный пакет не должен использовать стандартный URI EnterpriseData только ради сходства структуры: этот URI включает соответствующую специальную обработку. Для подготовки правил собственного контракта применяется [расширение КД 3.1](https://github.com/ShadobaAI/kafka-adapter-conv), когда стандартных возможностей недостаточно.

### Назначение произвольного формата

Собственный формат задаёт контракт обмена под конкретную предметную область и требования получателя. Он позволяет сохранить механизм КД 3.1 и преобразование метаданных 1С в XDTO, одновременно определить собственный набор сущностей, названия полей и объём передаваемых данных.

Основные задачи такого формата:

- обмен с системой, которая использует собственные названия и состав полей;
- передача ограниченного набора данных вместо полного представления бизнес-сущности;
- согласование единого контракта между несколькими конфигурациями 1С с разными метаданными;
- выделение самостоятельных единиц обмена: документа, элемента справочника, записи регистра или строки табличной части;
- представление ссылок UUID и согласование идентификации с внешней системой;
- отделение структуры сообщения от внутреннего устройства информационной базы.

Например, внешний получатель может ожидать товар с полями `id`, `sku`, `name` и `kind`. В одной конфигурации `sku` заполняется из кода справочника, в другой — из отдельного реквизита. Формат описывает одинаковую модель товара, а правила каждой конфигурации определяют её заполнение. Имена метаданных не становятся частью контракта автоматически.

Собственный формат особенно полезен, когда стандартная сущность EnterpriseData содержит лишние для обмена данные либо не соответствует принятой у получателя единице обмена. При этом собственный формат сам по себе не предоставляет готовую семантику стандартного EnterpriseData: значения полей, правила поиска, очистки и обновления должны быть согласованы участниками.

### Отличия от EnterpriseData

| Аспект | EnterpriseData | Произвольный формат |
| --- | --- | --- |
| Владелец модели | Стандартная модель 1С определённой версии. | Контракт конкретного решения или участников интеграции. |
| Пространство имён | URI семейства EnterpriseData, включающий версию. | Собственный URI, отличающийся от стандартного семейства. |
| Состав сущностей | Бизнес-сущности и свойства стандартного пакета. | Необходимые для сценария сущности и свойства. |
| Названия типов и полей | Названия стандартной модели. | Собственные названия, согласованные с правилами и механизмами распознавания адаптера. |
| Идентификация | Специальная обработка стандартных ключевых свойств и ссылки. | Поле ссылки конфигурации сопоставляется с полем формата через правила; стандартный блок ключевых свойств не возникает автоматически. |
| Ссылки | Типизированные потомки базового `Ref` стандартной модели. | Собственный `tns:UUID`; назначение конкретной ссылки задаётся полем и правилами. |
| Табличные данные | Стандартные типы таблиц и строк бизнес-сущности. | Собственные типы таблицы и строки с поддерживаемой структурой обёртки. |
| Самостоятельная строка | Наличие типа строки в пакете не задаёт самостоятельный сценарий обмена. | Строка может быть самостоятельной единицей обмена с собственным типом, ключом и контекстом владельца. |
| Конвертация | Правила должны соответствовать стандартной модели используемой версии. | Правила должны соответствовать собственному пакету и назначению полей. |
| Совместимость изменений | Зависит от версии стандартного пакета и правил конфигурации. | Поддерживается владельцами собственного контракта и правил. |

Произвольный формат не является «EnterpriseData с другими именами». Общим остаётся принцип типизированной модели и правил преобразования, но стандартные соглашения идентификации и бизнес-смысл не переносятся простым переименованием типов.

### Из чего состоит собственный формат

Полное описание формата включает не только перечень полей.

| Часть | Что определяет |
| --- | --- |
| Пространство имён пакета | Область принадлежности типов; вместе с именем типа используется для их выбора в фабрике XDTO. |
| Объектные типы сущностей | Набор данных каждой единицы обмена. |
| Простые типы и ограничения | Представление строк, чисел, дат, UUID и кодов перечислений; допустимые значения. |
| Свойства типов | Имена полей, типы, обязательность, повторяемость и допустимость пустого значения. |
| Типы таблиц и строк | Структуру коллекций строк внутри сущности. |
| Типы групп и составных значений | Представление вложенных данных с учётом специальных механизмов адаптера. |
| Зависимости пакетов | Используемые типы других пространств имён. |
| Семантика полей | Значение идентификаторов, единиц измерения, статусов, дат и других бизнес-данных. |
| Правила конвертации | Сопоставление модели формата с метаданными, преобразование значений и поиск объектов. |

XSD задаёт структурную часть модели, импортированная модель XDTO позволяет создавать и проверять экземпляры. Правила КД определяют переход между экземпляром этой модели и данными 1С. Соглашения участников определяют смысл сообщения и ожидаемый результат его обработки.

### Сущности, идентификаторы и связи

Объектный тип обычно описывает одну сущность, например `Product`, `Order` или `OrderLine`. Для типа должны быть определены данные идентификации и состав передаваемого состояния. Поле `id` может представлять ссылку объекта 1С, внешний идентификатор или иной ключ; назначение должно быть указано явно.

Ссылка на связанную сущность обычно передаётся отдельным UUID-полем, например `customerId` или `productId`. Такое поле не содержит данные связанного объекта. Для его разрешения получатель использует правила, соответствующие типу сущности. Если нужен текст для отображения, он может передаваться дополнительным обычным строковым полем, но не заменяет идентификатор.

Тип `UUID` задаёт представление и участвует в распознавании ссылки адаптером. Он не описывает, к какому справочнику относится конкретное поле. При общем UUID-типе именно контекст поля и ПКО должны различать, например, товар, контрагента и владельца строки. Наличие одинакового текста UUID в разных полях не делает их взаимозаменяемыми ссылками.

Если поиск выполняется по бизнес-ключам, формат должен содержать необходимые поля, например код или сочетание номера и даты. Уникальность этих ключей и приоритет поиска не определяются ограничением строкового XDTO-типа.

### Пример модели собственного документа

Ниже показан фрагмент XSD с простыми свойствами, ссылками и таблицей объектных строк. Пространства имён `xs` и `tns` предполагаются объявленными; `tns` связан с собственным URI пакета. Тип `UUID` определён в разделе о ссылках. Фрагмент описывает структуру, а не готовые правила конвертации.

```xml
<xs:complexType name="Order">
  <xs:sequence>
    <xs:element name="id" type="tns:UUID"/>
    <xs:element name="number" type="xs:string"/>
    <xs:element name="customerId" type="tns:UUID"
                minOccurs="0" nillable="true"/>
    <xs:element name="comment" type="xs:string" minOccurs="0"/>
    <xs:element name="lines" type="tns:Order.Lines" minOccurs="0"/>
  </xs:sequence>
</xs:complexType>

<xs:complexType name="Order.Lines">
  <xs:sequence>
    <xs:element name="row" type="tns:Order.Lines.Row"
                minOccurs="0" maxOccurs="unbounded"/>
  </xs:sequence>
</xs:complexType>

<xs:complexType name="Order.Lines.Row">
  <xs:sequence>
    <xs:element name="lineNo" type="xs:integer"/>
    <xs:element name="productId" type="tns:UUID"/>
    <xs:element name="quantity" type="xs:decimal"/>
  </xs:sequence>
</xs:complexType>
```

`Order` описывает документ. `id` должен быть связан правилами с идентификацией документа, `customerId` — с его контрагентом. `comment` допускает отсутствие, а `customerId` дополнительно допускает пустое значение. Различие проявляется в формировании сообщения, как описано в разделе о пустых значениях.

`Order.Lines` содержит ровно одно повторяющееся объектное свойство, поэтому соответствует табличной форме адаптера. `Order.Lines.Row` описывает реквизиты строки. Число `lineNo` не делает строку самостоятельной единицей обмена; для отдельного обмена строками нужны собственные правила и контекст владельца.

Обязательные `quantity` и `lineNo` должны получить допустимые значения. Если ноль является значимым значением, политика преобразования пустых значений должна сохранять его. Обязательность числового поля сама по себе не отключает преобразование нуля в незаполненное значение.

### Возможности и границы стандартной конвертации

Собственная модель допускает переименование полей, выбор передаваемых реквизитов, преобразование значений алгоритмами КД, собственные перечисления, ссылки UUID, табличные объекты и самостоятельные типы строк. Она также позволяет описывать данные, вычисленные по нескольким реквизитам, если правила возвращают результат требуемой формы.

Структура пакета должна соответствовать фактически используемой ветке конвертации. Особенно существенны следующие ограничения:

- обычная таблица объектов имеет обёртку с одним повторяющимся свойством строк;
- имя `UUID` участвует в распознавании ссылки, а ограничение строки длиной 36 символов само по себе не предоставляет такую семантику;
- произвольно именованный вложенный объект с несколькими полями при чтении может быть обработан как составное значение с выбором одного варианта;
- общие группы свойств используют соглашение об имени типа `ОбщиеСвойства`;
- свойство `AdditionalInfo` имеет специальную обработку;
- свойства из дополнительных пространств имён не включаются автоматически в обычное преобразование в структуру правил;
- обязательность и фасеты проверяют данные модели, но не определяют поиск, создание, обновление или очистку объекта 1С.

Поддержка типа платформой XDTO и поддержка его формы стандартной конвертацией адаптера — разные условия. Для вложенных объектов, рекурсивных связей и коллекций недостаточно того, что схема успешно импортируется: представление должно быть согласовано с классификацией свойств, правилами отправки и правилами получения.

### Развитие собственного контракта

Изменение имени поля, ссылочного типа, структуры таблицы, кодов перечисления или обязательности затрагивает сообщения и правила обеих сторон. Удаление необязательного поля и замена его на `null` также могут иметь разную семантику обновления.

Версия собственного формата должна отражать принятые участниками правила совместимости. Версия в URI пакета, версия менеджера КД и адрес Kafka-топика решают разные задачи: URI выбирает модель типов, версия менеджера определяет интерфейс конвертации, топик определяет маршрут сообщений. Совпадение или сходство этих строк не устанавливает автоматической связи между ними.

### Примеры форматов в репозитории

Материалы [прежних примеров XDTO](https://github.com/ShadobaAI/kafka-tools/tree/main/xdto/examples) иллюстрируют разные формы данных: [kfk-test.xsd](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/examples/kfk-test.xsd) — сущности справочника и регистров, UUID, перечисление и табличный объект; [asyncapi_example.xsd](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/examples/asyncapi_example.xsd) — ссылки, коллекции, вложенные объекты и ограничения значений; [kfk-unit.xsd](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/examples/kfk-unit.xsd) — разнообразные тестовые сочетания типов и границ.

Эти материалы не являются эталоном всех требований конвертации. В частности, `nillable="true"` без `minOccurs="0"` описывает обязательный элемент с допустимым пустым значением; произвольное имя многополевого вложенного типа не гарантирует чтение всех его полей; обёртка с повторяющимися простыми значениями не равнозначна таблице объектных строк. Такие конструкции оцениваются по модели и правилам адаптера, а не по названию примера или факту генерации XSD.

### Ссылки собственного формата: `tns:UUID`

В произвольном формате ссылка представляется собственным простым типом **UUID**. Обозначение `tns:UUID` в XSD означает тип из целевого пространства имён пакета; сам префикс `tns` не является частью имени типа.

```xml
<xs:simpleType name="UUID">
  <xs:restriction base="xs:string">
    <xs:pattern value="[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}"/>
  </xs:restriction>
</xs:simpleType>
<xs:element name="customerId" type="tns:UUID"/>
```

Фрагмент предполагает объявленные пространства имён `xs` и `tns`. Адаптер распознаёт ссылочную семантику по имени типа `UUID` без учёта регистра. Поэтому строка с длиной 36 символов или отдельный тип `CustomerId` с таким ограничением не равнозначны распознанному UUID-типу.

Распознавание по имени не означает автоматическое распознавание всех производных типов собственного UUID. Модель поля, используемого как ссылка, должна явно учитывать этот механизм.

Имя ссылочного поля произвольного формата определяется правилами: например, `id`, `ref` или согласованное имя. Для идентификации объекта должно быть задано соответствие между ссылкой конфигурации и полем формата. Наличие UUID-поля произвольного назначения не делает его автоматически идентификатором самого объекта.

### Идентификация в собственном формате

Для произвольного формата обязательность стандартного блока `КлючевыеСвойства` автоматически не вводится. Ссылка объекта может быть задана собственным полем UUID; соответствие ссылке конфигурации и поиск определяются правилами. Наличие поля `id` или `ref` без такого соответствия не включает стандартную обработку ключей EnterpriseData.

Идентификация при получении может использовать уникальный идентификатор либо сочетать поиск по идентификатору с последующим поиском по полям. Контракт должен содержать данные, необходимые выбранному варианту. Правила определяют, какие поля участвуют в поиске и допускается ли создание объекта. При использовании ключевых объектных типов необходимо учитывать соглашения распознавания вложенных свойств.

### Строка табличной части как самостоятельный объект

EnterpriseData уже содержит объектные типы строк таблиц. Отличие расширенного сценария адаптера заключается в **единице обмена**: строка может описываться и передаваться как самостоятельный объект, а не только внутри документа или справочника.

| Сценарий | Тело единицы обмена |
| --- | --- |
| Объект с табличной частью | Данные сущности и её таблица строк. |
| Строка как самостоятельный объект | Данные одной строки и необходимый контекст. |

Самостоятельная строка имеет собственный объектный тип формата. Обычно в нём необходимы ссылка на владельца и идентификация строки, а также её реквизиты.

| Пример поля | Назначение |
| --- | --- |
| `ownerId` | Ссылка UUID на владельца строки. |
| `lineId` или `lineNo` | Идентификация строки по правилам контракта. |
| `productId` | Ссылка UUID на товар. |
| `quantity` | Количество. |

Номер строки не является универсальным устойчивым идентификатором: вставка и перестановка строк могут его изменить. Требуемая устойчивость ключа и правила сопоставления определяются сценарием обмена.

Строка должна регистрироваться и обрабатываться как отдельная единица. Сам XDTO-пакет не создаёт подписку на изменение строки, не выполняет разбиение сообщения и не задаёт поиск владельца при получении.

[Пример разделения табличных данных](../user/examples/outgoing-split-rows.md) показывает регистрацию строк под отдельным ключом и отправку по принципу «одна строка — одно сообщение». В нём используются произвольные обработчики; пример иллюстрирует разделение и маршрутизацию, а не готовые правила КД для любой табличной части.

Для сценария КД необходимо согласовать объектный тип строки, правила заполнения и обработку источника. При получении правила отдельно определяют поиск владельца, поиск строки, обновление или добавление. Поддержка модели самостоятельной строки не означает автоматическое восстановление табличной части без этих правил.

## Общие требования конвертации

Этот раздел относится к обоим форматам. Унаследованная ветка EnterpriseData использует стандартные типы и соглашения; собственный формат должен согласовать свою модель с теми же механизмами обработки. Отличия в ссылках и идентификации описаны отдельно выше.

### Доступность пакетов и типов

Используемые типы должны быть доступны в глобальной фабрике XDTO конфигурации. Тип выбирается по пространству имён и имени, а не по имени файла схемы или подписи типа.

ПКО, указывающее объект формата, должно разрешаться в существующий тип XDTO. В правилах получения должно быть задано имя объекта выборки формата: оно определяет модель чтения входного тела. Зависимые пакеты также должны быть доступны. Для EnterpriseData это включает базовую модель ссылок `Ref`; для произвольного формата собственный тип `UUID` должен быть доступен в используемом пакете.

| Настройка адаптера | Значение для КД 3.1 |
| --- | --- |
| Тип сериализации продюсера | `Конвертация данных`. |
| Формат сериализации | URI пространства имён XDTO-пакета. |
| Имя ПОД сериализации | Имя правила обработки данных модуля обмена. |
| Тип десериализации консьюмера | `Конвертация данных`. |
| Формат десериализации | URI пространства имён XDTO-пакета. |
| Имя ПОД десериализации | Имя соответствующего правила обработки данных. |

Версия модели EnterpriseData и версия интерфейса менеджера обмена — разные понятия. Адаптер поддерживает интерфейс менеджера обмена с основной версией `2`; для менеджера расширенного формата также распознаётся окончание версии `.КФК`. Это не номер версии схемы данных.

### Представление сообщения

При отправке правила преобразуют данные 1С в структуру формата, по ней формируется объект XDTO, затем результат преобразуется в данные JSON. При получении тело JSON читается по выбранному типу XDTO, преобразуется в структуру для правил и далее — в данные конфигурации.

```text
Отправка: данные 1С → правила КД → структура формата → XDTO → JSON
Получение: JSON → XDTO → структура формата → правила КД → данные 1С
```

При отправке адаптер рекурсивно преобразует XDTO в данные сообщения: обычный `ОбъектXDTO` становится структурой, а `СписокXDTO` — массивом с преобразованием каждого элемента. Из `ЗначениеXDTO` извлекается свойство `Значение`; обычные значения типов 1С, включая `Неопределено`, сохраняются. Для [табличного объекта](#табличный-объект-и-строка) действует отдельное правило: служебный контейнер разворачивается в массив строк.

XSD описывает систему типов и не означает передачу XML в этом сценарии Kafka. Стандартный файловый протокол синхронизации EnterpriseData и формат тела сообщения адаптера также не следует считать одним и тем же контрактом только из-за общего пакета типов.

### Простые значения

Одиночное свойство типа значения XDTO обрабатывается как обычное свойство. Сюда относятся строки, числа, даты и логические значения. Тип готового пакета и правила определяют допустимое значение; подпись поля не меняет его тип.

При формировании обычного значения ссылка 1С может быть приведена к XML-представлению для создания значения нужного типа. Это не отменяет различия обычной строки и распознанного ссылочного типа: для ссылок предусмотрена отдельная семантика.

Необоснованное сужение диапазона числа, замена даты строкой или изменение точности должны рассматриваться как изменение контракта, а не как техническая деталь пакета.

### Перечисления

Перечисление формата распознаётся по фасетам перечисления простого XDTO-типа. Код обмена должен входить в допустимый набор значений типа.

| Источник при отправке | Преобразование |
| --- | --- |
| Строковый код формата | Создание значения enum-типа по этому коду. |
| Значение перечисления конфигурации | Поиск правила конвертации предопределённых данных и соответствующего кода отправки. |

При получении тип и код перечисления сохраняются для обратного преобразования. Поэтому пользовательское представление значения, его имя в конфигурации и код формата нельзя считать тождественными без правила соответствия.

Рекомендуемые подписи перечисления в документации не заменяют коды и не создают правила КД. Изменение кодов требует согласования обеих сторон обмена и таблиц конвертации значений.

### Табличный объект и строка

Табличная часть внутри сущности представляется объектом-обёрткой с **одним многозначным свойством**. Тип этого свойства описывает строку таблицы.

```text
Объект документа
  → свойство таблицы
    → объект-обёртка
      → многозначное свойство строк
        → объект строки с реквизитами
```

Адаптер определяет табличную форму по структуре: объектный тип имеет одно свойство, а его верхняя граница отличается от `1`. Для обычной таблицы объектов это свойство должно быть коллекцией объектных строк.

Имя свойства строк не фиксировано как `row`: при конвертации используется первое и единственное свойство типа таблицы. В EnterpriseData 1.25 встречается имя `Строка`; произвольный пакет может использовать `row` или другое согласованное имя.

При формировании исходящего сообщения служебный объект таблицы разворачивается в массив объектов строк: `"lines": [{...}, {...}]`. Поле коллекции строк (`row`, `Row`, `Строка` или другое имя) в JSON не передаётся. Правило действует рекурсивно, в том числе для корневой таблицы, которая становится корневым массивом. Обычные объекты с несколькими свойствами сохраняются как объекты. Контракт YAML должен описывать итоговый массив, даже если модель XDTO содержит контейнер.

Различия между `null`, пустой таблицей и пустыми элементами описаны в разделе [«Списки и табличные части»](#списки-и-табличные-части). Разворачивание контейнера описывает отправку; обратное чтение массива в табличный контейнер требует отдельной поддержки.

#### Ограничения табличной формы

Добавление второго свойства в тип-обёртку меняет его классификацию: такой тип больше не распознаётся как таблица по указанному правилу. Дополнительные поля контекста следует располагать в родительском объекте или в модели строки согласно контракту.

Верхняя граница свойства строк должна выражать коллекцию. Если она равна `1`, объект с единственным полем не распознаётся как таблица этим механизмом. Поэтому ограничение таблицы единственной строкой требует отдельного согласования с конвертацией.

Само структурное распознавание не доказывает корректность любого типа с одним повторяющимся свойством. Например, таблица объектов и обёртка массива примитивов не эквивалентны: обработчик таблицы ожидает модель свойств строки.

### Массивы простых значений

Простое свойство с верхней границей, отличной от `1`, распознаётся при формировании XDTO как массив обычных значений. Он заполняет многозначное свойство непосредственно и не является таблицей объектов.

Для такой коллекции тип элемента, допустимые значения и повторяемость относятся к самому свойству. Искусственная обёртка, похожая на объект таблицы, может изменить выбранный механизм конвертации.

Поддержку отправки массива простых значений не следует трактовать как доказательство симметрии всех вариантов чтения: обратное преобразование конкретной коллекции должно быть согласовано с правилами и проверено на экземплярах её модели.

### Общие и составные объектные свойства

Вложенное объектное свойство не всегда обрабатывается как обычная вложенная структура. Адаптер классифицирует его по форме, специальному имени свойства и имени типа.

| Признак модели | Обработка |
| --- | --- |
| Свойство `AdditionalInfo` | Произвольные данные через XDTO-сериализацию. |
| Табличная форма | Таблица объектов. |
| Имя типа содержит обозначение ключевых свойств | Ключевое объектное представление. |
| Имя типа содержит `ОбщиеСвойства` | Общая группа свойств. |
| Другой объектный тип | Составное значение с выбором заполненного варианта при чтении. |

Последовательность распознавания существенна: например, структурная табличная форма проверяется раньше соглашения об имени ключевого типа.

#### Общие свойства

Объектный тип с обозначением `ОбщиеСвойства` используется для группы вложенных данных. При формировании группа может заполняться из собственной вложенной структуры либо из текущего источника согласно результату правил.

Имя такого типа участвует в выборе механизма чтения. Поэтому простое переименование общего типа в произвольное бизнес-имя может изменить поведение, даже если состав его XSD-полей не изменился.

#### Составное значение

Для составного свойства объект формата содержит возможные варианты значения. При отправке правила могут задавать тип варианта через внутреннее описание `ТипСоставногоСвойства`. Адаптер выбирает подходящее свойство варианта и формирует объект составного типа.

При чтении составного объекта используется первое установленное свойство варианта, остальные не преобразуются как независимые поля этого же значения. Модель должна однозначно определять выбранный вариант; несколько одновременно заполненных вариантов не являются эквивалентом обычной структуры со всеми полями.

Следовательно, произвольно именованный вложенный тип с несколькими обычными реквизитами нельзя безусловно считать поддерживаемым вложенным объектом: он может попасть в ветку составного значения. Для группы реквизитов необходимо согласовать модель с механизмом общих свойств или соответствующими правилами.

#### Произвольные данные `AdditionalInfo`

`AdditionalInfo` имеет специальный смысл: значение преобразуется средствами XDTO-сериализации произвольных данных, а не обычным набором ПКС вложенного бизнес-объекта. Использование этого имени для несвязанного поля меняет его обработку.

Этот механизм не заменяет согласованный контракт основных полей. Получатель должен понимать назначение и представление дополнительных данных.

### Записи регистров и пакеты

Запись регистра может иметь собственный тип данных формата. Для регистров накопления, бухгалтерии, расчёта и регистров сведений в режиме подчинения регистратору предусмотрена пакетная модель: правила КД применяются к каждой выбранной записи, а одно сообщение содержит массив результатов.

Модель одиночной записи описывает элемент, а контракт пакета — всё тело сообщения. Пакет по регистратору и поток самостоятельных строк являются разными сценариями и должны различаться в настройках и ожиданиях получателя.

### Пустые значения и обязательность

Модель должна различать отсутствие свойства, явно переданное пустое значение и обычное значение, которое стандартная проверка 1С считает незаполненным. Это разные состояния. Например, отсутствие `Количество`, `"Количество": null` и `"Количество": 0` имеют разный смысл для получателя.

#### Обязательность, количество значений и допустимость null

| Характеристика | Описание | Требование к модели |
| --- | --- | --- |
| `minOccurs` в XSD | Задаёт минимальное количество появлений элемента. В XDTO соответствует `НижняяГраница`. Для одиночного свойства `0` допускает отсутствие, `1` требует присутствия. | Не должно подменяться признаком допустимости пустого значения. Если атрибут не указан в XSD, стандартное значение — `1`. |
| `maxOccurs` в XSD | Задаёт максимальное количество появлений. В XDTO соответствует `ВерхняяГраница`; одиночное значение и список обрабатываются по-разному. | Согласуется с формой данных: одиночное поле, повторяющиеся значения или строки таблицы. |
| `nillable` в XSD | Разрешает элемент с `xsi:nil="true"`. В XDTO соответствует `ВозможноПустое`: свойству разрешено значение `Неопределено`. | Допустимость `null` в контракте JSON должна согласовываться с этим разрешением. По умолчанию `nillable` равно `false`. |

`minOccurs="0"` разрешает не передавать элемент, но не разрешает передавать его с `nil`. `nillable="true"` разрешает пустое значение, но не отменяет требование присутствия при `minOccurs="1"`. Поэтому обязательное поле с допустимым `null` и необязательное поле без допустимого `null` являются самостоятельными вариантами модели.

Для XML-атрибутов обязательность задаётся `use`, а не `minOccurs`; `nillable` относится к элементам. Ниже рассматриваются свойства формата, представленные элементами XSD.

#### Общий контракт пустых значений

Для сообщения с полным состоянием объекта предусмотренные контрактом поля должны присутствовать в JSON. Допустимость пустого значения (`nullable`) и нижняя граница (`minOccurs`, `НижняяГраница` XDTO) рассматриваются совместно, независимо от того, является свойство одиночным или повторяющимся.

| Допускается пустое значение (`nullable`) | Нижняя граница | Пустой источник |
| --- | --- | --- |
| Да | `0` | Поле передаётся со значением `null`. |
| Да | `>0` | Допустимость пустого значения игнорируется; отсутствие требуемого значения является ошибкой. |
| Нет | `0` | Передаётся пустое значение, предусмотренное типом и контрактом поля; для массива — `[]`. |
| Нет | `>0` | Отсутствие требуемого значения является ошибкой. |

Заполненное значение проверяется по типу и ограничениям. Положительная нижняя граница требует заполнения; у повторяющегося свойства она дополнительно определяет минимальное количество элементов. Для одиночного свойства minOccurs не задаёт минимальную длину строки или минимальное числовое значение. Если разрешённое пустое значение для типа и контракта не определено, его нельзя произвольно подменять нулём, false, пустой строкой или пустым объектом.

Эта таблица задаёт целевой контракт формирования сообщения, а не стандартную семантику XML Schema. В самой XSD nillable=true разрешает nil независимо от minOccurs; игнорирование nullable при положительной нижней границе является правилом обработки адаптера. Описанное ниже текущее формирование одиночных свойств может отличаться от целевого контракта: например, сохранять null при minOccurs=1 или пропускать незаполненное поле при minOccurs=0 и nillable=false.

Для массивов есть нюансы представления. У простого списка minOccurs/maxOccurs повторяющегося свойства задают количество элементов. У таблицы эти границы задаются на свойстве строк внутри контейнера; minOccurs самого контейнера определяет его присутствие, а не количество строк. Разрешение null всего массива не разрешает null отдельных элементов. Если minOccurs отсутствует в XSD, стандартное значение равно 1.

Один атрибут nillable не обеспечивает null всего простого списка: у повторяющегося элемента он разрешает nil отдельного элемента. Выбор между null и [] и обязательный выпуск пустого поля требуют согласованной обработки адаптером. Предварительное присваивание пустого значения одиночным свойствам само по себе не обеспечивает такую обработку повторяющихся свойств.

#### Состояние свойства в XDTO

После создания объекта XDTO его свойства ещё не установлены: проверка `Установлено()` возвращает `Ложь`. Чтение значения и проверка установленности решают разные задачи. Одиночное свойство может возвращать значение по умолчанию, оставаясь неустановленным. Присваивание `Неопределено` свойству, допускающему пустое значение, устанавливает явное пустое значение; это не операция удаления свойства.

При формировании объекта формата адаптер заранее присваивает `Неопределено` **каждому одиночному свойству**, у которого `ВозможноПустое = Истина` и `ВерхняяГраница = 1`. Предварительное присваивание выполняется до поиска значения в структуре формата. Поэтому даже отсутствующее в структуре поле в этом случае становится установленным пустым свойством XDTO. Если затем найдено и успешно преобразовано заполненное значение, оно заменяет предварительное пустое значение.

У одиночного свойства без `ВозможноПустое` такого предварительного присваивания нет. Если источник отсутствует или его значение пропущено как незаполненное, свойство остаётся неустановленным. Отсутствие допустимо при нижней границе `0`; при обязательном свойстве модель должна получить значение, иначе объект не проходит проверку перед отправкой.

#### Когда поле становится null, а когда отсутствует

Следующая таблица описывает обычное одиночное свойство при отсутствии значения в структуре формата либо при его пропуске как незаполненного. Она не распространяется автоматически на списки, специальные составные свойства и свойства с отдельной пользовательской обработкой.

| `minOccurs` | `nillable` | Формирование XDTO | Представление поля в сообщении |
| --- | --- | --- | --- |
| `0` | `false` | Адаптер не присваивает значение; свойство остаётся неустановленным. | Поле отсутствует в JSON. |
| `0` | `true` | Адаптер заранее устанавливает `Неопределено`. | Передаётся явное пустое значение `null`, хотя модель допускает отсутствие поля. |
| `1` | `false` | Свойство остаётся неустановленным, требование обязательности не выполнено. | Успешное сообщение не формируется: объект должен пройти проверку XDTO до сериализации. |
| `1` | `true` | Адаптер заранее устанавливает `Неопределено`; присутствует допустимое пустое значение. | Передаётся `null`. Обязательность не означает наличие непустого бизнес-значения. |

Например, для необязательной строки с разрешённым пустым значением отсутствие исходного реквизита приводит к состоянию, представленному как:

```json
{"Комментарий": null}
```

Для необязательной строки без разрешённого пустого значения пропущенный реквизит не добавляется:

```json
{}
```

Если строка действительно сохранена как обычное значение, пустая строка имеет самостоятельное представление:

```json
{"Комментарий": ""}
```

Для обычного одиночного свойства различие между отсутствием и `null` определяется состоянием сформированного XDTO-объекта: неустановленное свойство пропускается, установленное пустое свойство включается в сообщение. `nillable` не является командой заменить произвольные значения на `null`: предварительное присваивание выполняет сам адаптер.

Если требуется контракт «поле может отсутствовать, но при наличии не может быть `null`», ему соответствует необязательное свойство без разрешённого пустого значения. Контракт «поле обязательно присутствует, значение может быть `null`» требует обязательного свойства с разрешённым пустым значением. Для контракта «поле может отсутствовать или содержать `null`» модель допускает оба состояния, однако стандартное формирование одиночного свойства адаптером выбирает явное пустое значение при отсутствии исходного значения.

#### Преобразование пустых значений в null

Название `ОтключитьПреобразованиеВNull` описывает результат на границе JSON. Внутри конвертации незаполненное значение преобразуется в `Неопределено`, а не непосредственно в значение 1С `Null`. Затем форма результата зависит от модели: разрешённое пустое одиночное свойство остаётся установленным пустым, необязательное свойство без такого разрешения пропускается, обязательное непустое свойство вызывает нарушение модели.

По умолчанию `ОтключитьПреобразованиеВNull = Ложь`. При выгрузке свойства используется стандартная проверка `ЗначениеЗаполнено`. Ноль, `Ложь`, пустая строка, пустая дата и пустая ссылка могут считаться незаполненными и попадать под эту обработку. Ноль и `false` поэтому нельзя считать безусловно сохраняемыми значениями только потому, что тип XDTO допускает число или булево значение.

Для сохранения обычных пустых значений при стандартном преобразовании свойства нужны одновременно два условия:

- `ОтключитьПреобразованиеВNull = Истина` в компонентах обмена;
- менеджер обмена распознан как менеджер Адаптера Kafka: версия менеджера заканчивается на `.КФК`.

| Менеджер `.КФК` | `ОтключитьПреобразованиеВNull` | Пустое обычное значение на этапе преобразования свойства |
| --- | --- | --- |
| Нет | `Ложь` | Преобразуется в `Неопределено`. |
| Нет | `Истина` | Преобразуется в `Неопределено`: одного параметра недостаточно. |
| Да | `Ложь` | Преобразуется в `Неопределено`. |
| Да | `Истина` | Сохраняется для последующего преобразования в значение XDTO. |

При формировании XDTO также учитывается этот параметр: `Null` и `Неопределено` всегда считаются незаполненными, а для остальных значений при включённом параметре стандартная проверка заполненности не служит причиной пропуска. Эта последующая проверка не восстанавливает значение, которое уже было заменено на `Неопределено` на предыдущем этапе.

Параметр не создаёт отсутствующие поля, не меняет `minOccurs` или `nillable` и не отменяет ограничения типа. Сохранённое значение должно подходить типу XDTO и его фасетам. Например, пустая строка не становится корректным UUID, а пустая дата не становится допустимой датой только из-за включения параметра.

Для явного исходного `Null` отключение преобразования не действует: он всё равно переводится в `Неопределено`. Исходное `Неопределено` также не становится обычным значением. Поэтому сохранение `0`, `false` и `""` нужно отличать от передачи явного `null` и от отсутствия значения.

#### Пустая ссылка и UUID

Признак ссылочного типа и заполненность ссылки проверяются на разных этапах. В произвольном формате ссылочное значение может быть описано через `tns:UUID`; распознавание UUID не отменяет общей обработки незаполненных значений.

При включённом преобразовании пустая ссылка может быть заменена на `Неопределено` до преобразования в строковое представление ссылки. При отключённом преобразовании для менеджера `.КФК` значение сохраняется и передаётся в преобразование ссылочного типа. Пустая ссылка, нулевой UUID, отсутствие поля и `null` не должны трактоваться как одно состояние без отдельного соглашения правил и получателя. Допустимость строкового значения UUID определяется типом и ограничениями пакета; смысл ссылки — правилами конвертации и поиска.

#### Списки и табличные части

Предварительное присваивание `Неопределено` применяется только при верхней границе `1`. Для повторяющегося свойства допустимость пустого значения относится к **элементу списка**, а не является автоматическим разрешением заменить весь массив на `null`.

При формировании исходящего сообщения существующая таблица без строк и пустой список XDTO становятся `[]`. Пустое одиночное табличное свойство сохраняет `null`, если это разрешено свойством XDTO; для табличного свойства без значения, не допускающего `null`, формируется `[]`. При преобразовании списка сохраняются порядок и количество элементов, включая пустые элементы. Эти правила применяются после проверки ограничений XDTO и не отменяют требования к минимальному количеству строк и допустимости пустых элементов.

При заполнении массива простых значений адаптер перебирает все исходные элементы. Незаполненный элемент преобразуется в `Неопределено` и добавляется в список; он не отбрасывается с уменьшением длины массива. При отключённом преобразовании обычные пустые значения сохраняются, но `Null` и `Неопределено` остаются пустыми. Если элементы не допускают пустого значения, модель не должна получать такие элементы: присваивание либо последующая проверка выявят нарушение.

Для модели таблицы нужно отдельно описывать обязательность объекта-контейнера и количество повторяющихся строк. Например, необязательный контейнер и обязательная строка внутри него означают, что контейнер можно не передавать, но переданный контейнер должен удовлетворять ограничению на строки. `minOccurs` строки не задаёт обязательность самого контейнера.

Отсутствующий список, пустой список, список с пустым элементом и таблица с пустой строкой имеют разные структуры. Таблица создаёт отдельный объект XDTO для каждой исходной строки; поля строки проходят ту же обработку одиночных свойств. Поэтому свойства строки могут стать `null` либо остаться неустановленными, а обязательные поля строки должны пройти проверку модели. Результат для пустого массива или контейнера нельзя выводить только из таблицы одиночных свойств выше.

#### Вложенные и составные свойства

Общие составные свойства формируются рекурсивно по специальной ветке до обычной проверки заполненности исходного значения. Для них отсутствие одноимённого вложенного поля может означать использование текущей структуры источника при заполнении вложенных свойств.

Результат такой группы принимается, если хотя бы одно вложенное свойство действительно заполнено либо если сама группа не допускает пустого значения. Поэтому непустое объектное представление группы и `null` определяются не только наличием поля в исходной структуре. Группа без заполненных дочерних полей может быть создана как объект, после чего обязательность дочерних свойств проверяется по XDTO-модели.

Ключевые свойства, общие свойства, варианты составного значения и табличные контейнеры требуют согласования с соответствующей специальной обработкой. Нельзя распространять правило «нет исходного поля — нет поля JSON» на все объектные свойства формата.

#### Значения по умолчанию

`default` в XSD и политика обработки пустых значений решают разные задачи. Значение по умолчанию может читаться из неустановленного одиночного свойства XDTO, но само по себе не означает, что адаптер явно заполнил поле данными конвертации. Явное присваивание `Неопределено` разрешённому пустому свойству является другим состоянием и не должно считаться запросом подставить значение по умолчанию.

Если контракт требует обязательного присутствия конкретного значения в JSON, его заполнение должно быть обеспечено правилами и согласовано с моделью. Наличие `default` не заменяет это требование. Фиксированное значение также должно соответствовать итоговым данным объекта.

#### Чтение null и отсутствующих полей

При получении JSON сначала читается в XDTO по выбранному типу. Затем при преобразовании XDTO в структуру формата адаптер учитывает установленность свойства и принадлежность его пространства имён базовым схемам.

Неустановленное свойство не переносится в структуру правил. Для обычной обработки установленное свойство со значением `Неопределено` также пропускается, если не задана отдельная обработка с явным типом. Поэтому наличие `null` во входном JSON не гарантирует наличия одноимённого поля со значением `Null` в структуре, которую получат правила КД. На этом этапе различие между отсутствием и явным пустым значением может быть утрачено.

Отсюда следует требование к сценариям обновления: передача `null` не является универсальной командой очистки реквизита объекта 1С. Поведение отсутствующего значения, очистка, сохранение прежнего значения и подстановка значения по умолчанию должны определяться правилами конвертации. Поддержку такой семантики нельзя выводить только из `nillable` пакета.

### Пространства имён свойств и расширения пакета

Конвертация учитывает не только URI типа, но и URI XML-представления свойства. В базовые схемы включаются выбранное пространство имён формата и `http://www.1c.ru/SSL/Exchange/Message`.

При чтении свойств в структуру применяется проверка их принадлежности базовым схемам. Поэтому добавление свойства из другого пространства имён не означает автоматическую передачу его в ПКС обычного объекта.

Для расширенных свойств предусмотрены специальные механизмы сопоставления типов и дополнения XDTO-объекта. Дополнительный пакет, его зависимости и правила должны быть согласованы с ними. Открытый тип или допустимое расширение XSD сами по себе не гарантируют чтение всех произвольных внешних свойств.

### Проверка перед отправкой

После формирования объекта формата адаптер выполняет проверку XDTO-модели до получения результата сообщения. При ошибке контекст включает ПОД, ПКО и имя типа XDTO; результат не должен считаться успешно сформированным сообщением.

Проверка модели выявляет нарушения заполнения и структуры, но не определяет бизнес-смысл данных. Например, корректный UUID может относиться к неверному объекту, а допустимый код перечисления — неправильно соответствовать значению конфигурации. Такие соответствия относятся к правилам конвертации.

Изменение пакета требует согласования обеих сторон: доступности типов, имён и структуры свойств, ссылок, таблиц, вариантов значений и правил поиска. Успешный импорт XSD не заменяет проверку фактических примеров обмена в обоих направлениях.
