# XDTO: модель данных обмена

XDTO (XML Data Transfer Objects) — механизм объектного моделирования данных, описанных схемой XML. В 1С он позволяет определить систему типов и значений для взаимодействия с другими системами. Основные понятия механизма приведены в [документации платформы 1С](https://v8.1c.ru/platforma/xdto/).

## XDTO и XSD

XDTO — модель типов и объектов в 1С, а XSD — описание этой модели в формате XML Schema. XSD описывает систему типов средствами XML Schema, а XDTO-пакет представляет эту систему в объектной модели 1С.

```text
XML Schema (XSD) → модель типов XDTO → значения и объекты XDTO
```

Описание типа и экземпляр данных различаются. Схема заказа определяет поля и их типы; конкретный заказ содержит значения этих полей. XSD и XDTO-пакет описывают типы, а не конкретные экземпляры данных.

### Уровни представления

| Уровень | Что описывает | Пример |
| --- | --- | --- |
| Схема XSD | XML-представление системы типов | Сложный тип заказа с элементами `number` и `lines`. |
| Модель XDTO | Типы и свойства, доступные в 1С | Тип объекта заказа, тип строки и многозначное свойство. |
| Экземпляр XDTO | Конкретное состояние объекта | Заказ с номером `ORD-001` и двумя строками. |
| Сериализованные данные | Представление экземпляра для передачи | XML-документ с данными объекта. |

Эти уровни связаны, но не взаимозаменяемы. Например, корректная схема не гарантирует заполненность конкретного заказа, а наличие объекта в памяти не означает, что его представление соответствует контракту получателя.

Схема XML и модель XDTO также не обязательно преобразуются друг в друга без изменений. Для полного сохранения представления при цикле «XSD → XDTO → XSD» важны правила оформления схем и поддерживаемые возможности модели. Поэтому XSD является описанием модели, но не обещанием побайтового воспроизведения исходного файла после экспорта.

## Фабрика XDTO

Фабрика XDTO объединяет описания типов, с которыми работает модель, и обеспечивает создание значений и объектов этих типов. Типы внутри фабрики сгруппированы в пакеты.

Фабрика является самодостаточной: типы могут ссылаться только на другие типы, входящие в ту же фабрику. Если пакет зависит от типов другого пространства имён, соответствующий пакет также должен быть представлен в фабрике.

В конфигурации существует глобальная фабрика XDTO. Она включает описания типов платформы, типов конфигурации и пакетов, заданных в метаданных. Отдельная фабрика может быть сформирована на основании набора XML-схем для собственной модели обмена.

Важно различать фабрику и пакет: пакет описывает типы одного пространства имён, а фабрика может объединять несколько пакетов и, соответственно, несколько схем.

### Глобальная и отдельная фабрики

| Фабрика | Состав и назначение |
| --- | --- |
| Глобальная фабрика конфигурации | Создаётся платформой и объединяет типы платформы, модели конфигурации и явно заданных XDTO-пакетов. |
| Отдельная фабрика | Описывает самостоятельную систему типов из подготовленного набора схем, например внешнего контракта обмена. |

Обычная отдельная фабрика формируется сразу со всеми необходимыми описаниями. Последовательное добавление типов в неё по одному не является общей моделью работы. Добавление пакетов через метаданные конфигурации относится к глобальной фабрике и не означает, что любой фабрике можно произвольно дописывать типы во время работы.

Самодостаточность важна при разделении контракта на пакеты. Если тип заказа использует тип адреса из другого пакета, одной схемы заказа недостаточно: фабрика должна знать оба описания. Наличие URL другого пространства имён само по себе не загружает его типы.

## Пакет и пространство имён

XDTO-пакет объединяет связанные типы. Пространство имён идентифицирует пакет и отличает его типы от одноимённых типов других пакетов.

Например, `http://example.com/crm` может обозначать пакет контракта CRM. Это идентификатор пространства имён модели. В XSD ему соответствует `targetNamespace`.

Для однозначного выбора типа важны пространство имён и имя типа. Вместе они образуют идентификатор типа. Название топика и читаемая подпись типа не заменяют эти сведения.

Пакет может содержать зависимости от других пакетов и глобальные свойства. Зависимость обозначает использование типов или глобальных свойств другого пространства имён.

Взаимные ссылки между типами и циклы директив импорта или включения XSD — разные ситуации. Для механизма XDTO циклический импорт и включение XSD-схем не поддерживаются.

### Идентичность типа

Типы `Order` из пространств имён `http://example.com/crm` и `http://example.com/erp` являются разными типами, даже если их поля совпадают. Напротив, одинаковые имя и пространство имён должны обозначать одно согласованное описание.

Префиксы XML вроде `tns`, `crm` или `erp` являются сокращениями URI, действующими в конкретном документе. Замена префикса при сохранении URI не создаёт новый тип. Замена URI меняет идентичность типа, даже если локальное имя остаётся прежним.

Для обмена существенно согласование пространства имён пакета, а не произвольный вид префикса в XSD. 

## Типы значений

Типы значений описывают простые данные: строки, числа, логические значения, даты и перечисления. В XSD они представляются встроенными типами или `xs:simpleType` с ограничениями.

Описание простого типа может строиться тремя способами:

| Способ | Смысл |
| --- | --- |
| Ограничение базового типа | Новый тип допускает подмножество значений базового типа. |
| Объединение типов значений | Значение принадлежит одному из включённых простых типов. |
| Список значений | Одно простое значение представляет список элементов заданного типа. |

Ограничение уточняет допустимые значения, например длину строки, диапазон числа или набор кодов статуса. Простое значение не имеет набора вложенных именованных полей. Список как способ определения простого типа не следует смешивать с повторяющимся свойством объекта.

Встроенные простые типы относятся к пространству имён `http://www.w3.org/2001/XMLSchema` и соответствуют системе типов XML Schema. Собственные типы могут уточнять их ограничениями.

### Фасеты

Фасеты — ограничения множества значений простого типа. Каждое ограничение имеет имя и значение; применимость зависит от базового типа.

| Ограничение | Назначение |
| --- | --- |
| Длина, минимальная и максимальная длина | Ограничивают длину значения. |
| Минимальная и максимальная граница | Определяют диапазон с включением или исключением границы. |
| Образец | Ограничивает форму значения регулярным выражением. |
| Перечисление | Задаёт набор допустимых значений. |
| Общее количество разрядов | Ограничивает количество цифр числа. |
| Количество дробных разрядов | Ограничивает цифры дробной части. |
| Обработка пробельных символов | Определяет сохранение, замену или сворачивание пробелов и других пробельных символов. |

Фасет не меняет назначение базового типа. Ограничение длины строки не делает её ссылкой на объект, а ограничение числа не превращает его в текстовый код.

### Ограничение, объединение и список

Ограничение сохраняет базовую природу значения. Например, код длиной не более двадцати символов остаётся строкой; денежная величина с двумя дробными разрядами остаётся числом. Все заданные ограничения применяются совместно.

Объединение позволяет одному простому значению принадлежать нескольким допустимым типам. Оно не образует объект с полями этих типов. При неоднозначной лексической форме, например тексте `001`, выбор строкового или числового смысла должен определяться моделью, а не только внешним видом значения.

Список простого типа представляет одно значение, состоящее из элементов заданного типа. В XML-схеме это механизм простого типа-списка. Коллекция объектов с повторяющимися XML-элементами относится к многозначному свойству и имеет другое устройство.

UUID в контракте представляет идентификатор в строковой форме. Его назначение отличается от объекта со всеми данными: идентификатор покупателя не содержит имя, адрес и другие свойства покупателя.

## Типы объектов и свойства

Тип объекта описывает структуру с именованными свойствами. В XSD ему соответствует `xs:complexType`.

Пример модели заказа:

| Свойство | Данные |
| --- | --- |
| `id` | UUID заказа. |
| `number` | Строковый номер. |
| `createdAt` | Дата-время. |
| `deliveryAddress` | Вложенный объект адреса. |
| `lines` | Коллекция строк заказа. |

Имя свойства определяет его место в данных, тип — допустимое значение, обязательность — возможность отсутствия. Вложенный объект имеет собственные свойства и собственные требования к ним.

Тип объекта может иметь базовый объектный тип и включать унаследованные свойства. Дополнительные характеристики определяют, допускаются ли неописанные свойства, является ли тип абстрактным и насколько важен порядок XML-элементов.

| Характеристика | Смысл |
| --- | --- |
| Открытый тип | Объект может содержать дополнительные свойства, не перечисленные в типе. |
| Абстрактный тип | Тип служит основой модели и не предназначен для непосредственного экземпляра. |
| Упорядоченность | Определяет требования к порядку элементов, представляющих свойства. |
| Последовательность | Позволяет явно представить порядок содержимого, когда одного порядка свойств недостаточно. |
| Смешанное содержимое | Допускает сочетание текста и вложенных элементов; требует представления последовательности. |

### Наследование и открытость

Базовый тип объекта задаёт общую систему свойств. Производный тип содержит как собственные, так и унаследованные свойства. Это отличается от поля, содержащего вложенный объект: наследование расширяет описание самого типа, а вложенное свойство добавляет отдельный уровень данных.

Открытость определяет возможность появления свойств сверх явно перечисленных. Она не означает отсутствие проверки известных свойств. Для закрытой модели набор свойств фиксирован описанием типа.

### Порядок и последовательность

Упорядоченность определяет допустимый порядок XML-элементов. Последовательность хранит порядок конкретного содержимого, когда его нельзя полностью выразить одним списком свойств типа.

Пример различия: поля `number`, `date` и `total` могут иметь фиксированный порядок в XML. Смешанное содержимое вида «текст — вложенный элемент — текст» требует хранить не только значения свойств, но и расположение текстовых фрагментов относительно элементов.

Смешанное содержимое не равно обычному строковому полю. Оно представляет текст и вложенные элементы в одном XML-содержимом. 

### Описание свойства

| Характеристика свойства | Назначение |
| --- | --- |
| Имя | Идентифицирует свойство внутри типа; имена должны быть уникальными. |
| Тип | Определяет простое значение или вложенный объект. |
| Нижняя граница | Минимальное количество значений свойства. |
| Верхняя граница | Максимальное количество значений; в XSD ей соответствует `maxOccurs`. |
| Возможность пустого значения | Определяет допустимость специального неопределённого значения, представляемого как `xsi:nil="true"`. |
| Значение по умолчанию | Задаёт исходное значение одиночного свойства согласно модели. |
| Фиксированное значение | Указывает, что значение свойства закреплено моделью. |
| Форма XML | Определяет представление как элемент, атрибут или текст. |

При построении модели из XSD имена свойств приводятся к правилам встроенного языка 1С. Например, точка или дефис в XML-имени могут заменяться подчёркиванием. Поэтому совпадение исходного XML-имени и имени свойства XDTO не следует предполагать для любого набора символов. Для контракта обмена предпочтительны имена, не требующие такого преобразования.

### Имя свойства и XML-имя

Свойство имеет имя в объектной модели и сведения о своём XML-представлении: локальное имя и URI пространства имён. Они отвечают на разные вопросы: каким именем свойство доступно в модели и как оно записывается в XML.

Если в схеме есть атрибут и элемент с одинаковым именем, при построении модели требуется различить их свойства. Платформа может расширить дублирующее имя числовым суффиксом. Поэтому одинаковый текст имени в XML не всегда означает одно свойство XDTO.

### Формы представления

| Форма | XML-пример | Особенности |
| --- | --- | --- |
| Элемент | `<number>ORD-001</number>` | Может представлять одиночное значение, повторяющиеся значения или вложенный объект. |
| Атрибут | `<order number="ORD-001"/>` | Не представляет несколько значений свойства как повторяющиеся одноимённые атрибуты. |
| Текст | `<amount currency="RUB">125.50</amount>` | Значение находится непосредственно в текстовом содержимом объекта. |

Для текстовой формы у типа предусмотрено одно текстовое свойство; остальные свойства такого представления имеют форму атрибутов. Это отличается от смешанного содержимого с произвольным чередованием текста и элементов.

Специальное пустое значение с `xsi:nil` относится к элементной форме. Атрибут XML не получает такой же механизм просто из-за необязательности соответствующего свойства.

## Коллекции

Коллекция представляет повторяющиеся значения одного описанного вида: строки, идентификаторы или объекты. Описание коллекции определяет тип элемента и ограничения количества.

Свойство с верхней границей больше единицы является многозначным и представляется списком. Неограниченной верхней границе соответствует `unbounded` в XSD и значение `-1` в описании границы XDTO.

Значение по умолчанию одиночного свойства не означает заполнение многозначного свойства элементами: список при создании объекта изначально пуст.

| Границы свойства | Смысл |
| --- | --- |
| Нижняя `0`, верхняя `1` | Необязательное одиночное значение. |
| Нижняя `1`, верхняя `1` | Обязательное одиночное значение. |
| Нижняя `0`, верхняя больше `1` | Коллекция, которая может не содержать значений. |
| Нижняя больше `0`, верхняя больше `1` | Коллекция с требованием минимального количества. |
| Верхняя `-1` | Количество сверху не ограничено. |

Для списка важен порядок его элементов. Это порядок значений конкретного многозначного свойства, а не порядок всех свойств объекта. Наличие списка не означает необходимость смешанного содержимого или отдельной последовательности XDTO.

Если модель разрешает специальное пустое значение многозначного свойства, оно относится к элементам списка. Пустая коллекция и коллекция с одним пустым элементом остаются разными данными.

## Отсутствие, пустое значение и `nil`

Отсутствие свойства, пустая строка, пустая коллекция и специальное пустое значение являются разными состояниями данных. Контракт должен определять их отдельно.

В XML Schema возможность отсутствия элемента задаётся `minOccurs`, а допустимость присутствующего элемента с `xsi:nil="true"` — `nillable`. Их различие описано в [XML Schema: объявления элементов](https://www.w3.org/TR/xmlschema-1/#Element_Declaration_details). Эти состояния имеют разный смысл в модели данных.

| Состояние | Пример XML | Смысл |
| --- | --- | --- |
| Элемент отсутствует | Нет элемента `comment` | Значение не представлено в документе. |
| Пустая строка | `<comment/>` для строкового типа | Представлено строковое значение без символов. |
| Специальное пустое значение | `<comment xsi:nil="true"/>` | Представлено неопределённое значение при разрешённом `nillable`. |
| Пустая коллекция | Нет элементов, представляющих значения многозначного свойства | Коллекция содержит ноль значений. |

Префикс `xsi` в примере обозначает пространство имён `http://www.w3.org/2001/XMLSchema-instance`.

Пустая строка может быть запрещена фасетом минимальной длины, даже если поле необязательно. Пустая коллекция может быть запрещена нижней границей количества, даже если предусмотрена возможность отсутствия её обёртки. Обязательное поле не обязательно непусто: это определяется типом и ограничениями.

### Значение по умолчанию и установленность

Одиночное свойство может получить значение по умолчанию при создании объекта, но при этом ещё не считаться явно установленным. Поэтому проверка «есть доступное значение» и проверка «значение установлено» отвечают на разные вопросы.

Фиксированное значение сильнее значения по умолчанию: оно закрепляет допустимое значение свойства моделью. Значение по умолчанию задаёт исходное состояние и само по себе не означает запрет другого допустимого значения.

## Экземпляры данных

Модель типов определяет допустимую структуру, а экземпляры содержат конкретные данные. Для простого типа экземпляром является значение XDTO; для объектного типа — объект XDTO с состоянием его свойств.

Простое значение связывает тип и само значение. Объект хранит значения одиночных свойств и списки многозначных свойств. Сведения о том, установлено ли свойство явно, отличаются от наличия исходного значения по умолчанию.

Рекурсивное описание типов не равнозначно циклическому графу экземпляров. Ссылки между объектами XDTO в значениях свойств не могут образовывать цикл. Это важно отличать от повторного использования схемы типа и от UUID-ссылок на внешние объекты.

Простые значения XDTO неизменяемы. Объект XDTO, напротив, имеет изменяемое состояние: значения его свойств могут заполняться, сбрасываться, а многозначные свойства — изменяться как списки.

У простого значения различаются само значение и лексическое представление. Например, число и текст, которым оно записано в XML, относятся к разным уровням представления. Лексическая форма должна быть допустима для выбранного типа; произвольный текст не становится датой только потому, что ему назначено описание даты.

### Проверка данных

Проверка заполнения объекта сопоставляет количество значений свойств с их границами и учитывает порядок содержимого, предусмотренный моделью. Проверяются также вложенные объекты. Первое нарушение может прервать проверку, поэтому отсутствие других сообщений об ошибках не является доказательством их отсутствия.

Пригодность модели, допустимость значений и корректность сериализованного документа являются отдельными уровнями проверки:

- Проверка модели выявляет несовместимые типы, зависимости и описания свойств.
- Проверка экземпляра выявляет несоответствие заполненных данных модели.
- Проверка представления сопоставляет полученный XML с XML-схемой.

Успешное создание объекта не заменяет все эти проверки. Также корректность XML-схемы не доказывает правильность правил заполнения данных из прикладных объектов.

## Сериализация и формат обмена

Сериализация преобразует значения и объекты в представление для хранения или передачи; десериализация восстанавливает данные из этого представления. XDTO изолирует работу с типами и свойствами от части деталей XML, но правила имён, порядка, форм свойств и пустых значений остаются существенными.

В платформе есть XML-сериализация на основе XDTO, в том числе для типов конфигурации. Она использует систему типов соответствующей фабрики. Состав типов фабрики определяет модель, используемую для сериализации.

## Пример соответствия XSD и XDTO

Фрагмент XSD описывает заказ с обязательным номером, необязательным комментарием и коллекцией строк:

```xml
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema"
           xmlns:tns="http://example.com/crm"
           targetNamespace="http://example.com/crm"
           elementFormDefault="qualified">
  <xs:complexType name="OrderLine">
    <xs:sequence>
      <xs:element name="quantity" type="xs:decimal"/>
    </xs:sequence>
  </xs:complexType>
  <xs:complexType name="Order">
    <xs:sequence>
      <xs:element name="number" type="xs:string"/>
      <xs:element name="comment" type="xs:string" minOccurs="0"/>
      <xs:element name="line" type="tns:OrderLine"
                  minOccurs="0" maxOccurs="unbounded"/>
    </xs:sequence>
  </xs:complexType>
</xs:schema>
```

В модели XDTO этому соответствуют два типа объектов, `Order` и `OrderLine`, из пространства имён `http://example.com/crm`.

| Свойство | Тип | Нижняя граница | Верхняя граница |
| --- | --- | --- | --- |
| `Order.number` | Строка | `1` | `1` |
| `Order.comment` | Строка | `0` | `1` |
| `Order.line` | Объект `OrderLine` | `0` | Не ограничена |
| `OrderLine.quantity` | Десятичное число | `1` | `1` |

`number` должен присутствовать, но без ограничения длины может быть пустой строкой. `comment` может отсутствовать; специальное значение `nil` ему не разрешено. `line` является многозначным свойством и может содержать ноль строк. Если строка присутствует, её `quantity` обязательно.

## Список и последовательность XDTO

Список XDTO и последовательность XDTO решают разные задачи. Список хранит значения одного многозначного свойства. Последовательность хранит порядок элементов и текстовых фрагментов всего содержимого объекта.

| Характеристика | Список XDTO | Последовательность XDTO |
| --- | --- | --- |
| Область действия | Одно многозначное свойство. | Содержимое объекта с последовательностью. |
| Состав элемента | Значение допустимого для свойства типа. | Пара «свойство — значение» либо текстовый фрагмент. |
| Порядок | Порядок значений в коллекции. | Порядок XML-элементов и текста. |
| Текстовые фрагменты | Не являются отдельным механизмом списка. | Допустимы для смешанного содержимого. |
| Специальное пустое значение | Возможно, если разрешено описанием свойства. | Значение определяется соответствующим свойством; отсутствие свойства в паре обозначает текстовый фрагмент. |

### Состояние списка

Список является упорядоченным набором простых значений или объектов допустимого типа. При вставке и удалении меняются позиции последующих элементов; замена меняет значение на существующей позиции.

Для каждого элемента списка нет отдельного понятия установленности свойства. Наличие нулевого количества элементов, наличие одного пустого значения и наличие одного заполненного объекта являются различными состояниями.

Нижняя и верхняя границы задаются описанием многозначного свойства. Изменение списка и проверка полного состояния объекта — разные операции: допустимость типа очередного элемента не доказывает соблюдение всех требований к количеству и остальным свойствам.

### Состояние последовательности

В последовательности фиксируется, как содержимое объекта выглядит в XML. Например, два значения разных свойств могут чередоваться с фрагментами текста. Обычного перечня свойств и отдельных списков тогда недостаточно для восстановления документа.

В последовательность входят свойства элементной формы: порядок XML-атрибутов не имеет такого значения для модели. Текстовые фрагменты допустимы только при смешанном содержимом. Порядок заполнения свойств объекта с последовательностью отражается в его последовательности.

Таким образом, последовательность — часть состояния экземпляра, а не просто порядок объявления свойств типа. Два объекта с одинаковыми значениями свойств могут требовать различного порядка содержимого, если модель это допускает.

## Навигация по дереву объектов

Для обращения к вложенным данным XDTO используется ограниченный язык путей, основанный на XPath. Он является модифицированным подмножеством XPath, поэтому возможности полного языка XPath нельзя автоматически считать доступными.

Основная конструкция — путь из шагов, разделённых `/`. Имя свойства выбирает соответствующее свойство; `.` обозначает текущий объект, `..` — объект-владелец. Начальный `/` задаёт отсчёт от корня дерева.

| Путь | Смысл |
| --- | --- |
| `Number` | Свойство текущего объекта. |
| `Address/City` | Свойство `City` вложенного объекта `Address`. |
| `.` | Текущий объект. |
| `..` | Объект-владелец. |

Если свойство в пути не найдено, обращение завершается ошибкой. При обращении к многозначному свойству результатом может быть весь список значений; такой результат нельзя считать одним объектом без дополнительного выбора.

Путь использует свойства объектной модели. Если XML-имя было нормализовано при построении XDTO, исходное написание имени XML не обязательно совпадает с шагом пути.

## Рекомендации по описанию XML-схемы

Механизм XDTO поддерживает более широкую модель, чем наиболее удобный профиль обмена объектными данными. Рекомендации по оформлению XML-схем направлены на сохранение эквивалентности при преобразовании «набор схем → фабрика → набор схем», надёжность проверки экземпляров и корректность полиморфного представления.

Эти рекомендации не следует смешивать с абсолютным запретом всех остальных конструкций XML Schema. Например, модель может содержать анонимный тип, но именованные типы предпочтительны для устойчивого преобразования и повторного использования.

### Именованные типы

Для схем обмена рекомендуется определять типы отдельно с явными именами и ссылаться на них из элементов. Непосредственно вложенное анонимное определение не даёт такого же явного идентификатора, как пара «пространство имён — имя».

```xml
<xs:complexType name="PersonType">
  <xs:sequence>
    <xs:element name="FirstName" type="xs:string"/>
    <xs:element name="FamilyName" type="xs:string"/>
  </xs:sequence>
</xs:complexType>
<xs:element name="Person" type="tns:PersonType"/>
```

Фрагмент предполагает объявленные префиксы `xs` и `tns`. Тип объявлен на уровне схемы, а элемент ссылается на него; определение типа не вложено внутрь элемента со ссылкой `type`.

### Единственная модель `sequence`

Для содержимого сложного типа предпочтителен один блок `sequence` без изменения стандартных границ повторения самого блока. Повторяемость отдельных свойств задаётся на соответствующих элементах.

Модель `all` допускает произвольный порядок входных элементов, но имеет ограничения на их повторяемость. Модель `choice` описывает выбор и может нарушать эквивалентность схем при преобразовании через XDTO. Проверка заполнения объекта при такой модели не равна полной проверке условий выбора исходной XML-схемы.

Комбинации нескольких моделей содержимого и повторяемая группа `sequence` также требуют более сложного представления. Они не должны считаться эквивалентными обычному объекту с независимыми свойствами только из-за одинакового набора имён.

### Элементы вместо атрибутов

Для объектного обмена предпочтительно представление свойств XML-элементами. Атрибуты имеют ограничения: не представляют вложенный объектный тип или многозначное свойство как набор повторяющихся значений.

При полиморфизме элемент позволяет указать фактический тип значения через `xsi:type`. Для атрибутного представления значение приводится к типу свойства, что может повлиять на сохранение фактического производного типа.

`simpleContent` сложного типа опирается на текстовое содержимое и атрибуты, поэтому не является предпочтительным способом представления обычного объекта с набором элементных свойств. Одинаковые имена атрибута и элемента также нежелательны из-за нормализации имён свойств XDTO.

### Смешанное содержимое

Смешанное содержимое оправдано, когда текст и элементы действительно должны чередоваться, например в текстовом документе с вложенной разметкой. Для обмена структурированными объектами оно усложняет модель: экземплярам требуется последовательность, а заполнение отдельных свойств не полностью описывает содержимое.

Поэтому mixed content не рекомендуется как универсальная форма для данных, которые естественно описываются обычными свойствами объектов.

## Правила корректности модели XDTO

Корректность фабрики включает проверку пакетов, типов, свойств и фасетов. Успешная проверка конкретного экземпляра не заменяет корректность самой модели.

### Фабрика и пакеты

- Пакеты внутри одной фабрики имеют уникальные URI пространства имён.
- Импорт указывает существующий пакет с непустым URI.
- Зависимости пакетов не образуют циклы импорта.
- Используемые внешние типы входят в объявленные зависимости и доступны в той же фабрике.
- Имена глобальных свойств непусты и уникальны в пределах пакета.
- Тип глобального свойства разрешается в пакете или его зависимостях.
- Одновременное именованное и анонимное определение одного типа свойства не допускается.

Глобальное свойство пакета отличается от свойства конкретного объектного типа: оно имеет собственное определение на уровне пакета и не задаёт границы повторения так же, как поле объекта.

### Типы значений

Именованный простой тип имеет непустое уникальное имя среди всех типов пакета. Анонимное определение, вложенное в другое описание, не получает такого же самостоятельного имени пакета.

Базовый тип простого типа также является типом значения. Тип не может ссылаться на самого себя по цепочке базовых типов, элементов списка или членов объединения. Такие циклы не создают допустимое определение простого значения.

Элемент простого типа-списка должен быть атомарным типом либо объединением атомарных типов. Это не механизм списка вложенных объектов. Для объединений состав и допустимость членов проверяются с учётом их варианта; произвольное вложение объединений не следует считать автоматически корректным.

Фасеты должны соответствовать примитивному предку и варианту типа. Набор ограничений атомарного типа, списка и объединения различается. Унаследованные ограничения должны оставаться согласованными с эффективными ограничениями базового типа.

### Типы объектов и свойства

Именованный объектный тип имеет непустое уникальное имя в пакете. Его базовый тип является объектным типом и не совпадает с самим определяемым типом.

Каждое свойство имеет непустое уникальное имя. При ссылке на именованный тип этот тип должен существовать; параллельное анонимное определение того же свойства не допускается. Уникальность требуется и для XML-представления свойств, а не только для их имён в объектной модели.

Нижняя граница количества является неотрицательным целым. Верхняя — неотрицательным целым либо `-1` для неограниченной повторяемости. При конечной верхней границе нижняя не должна превышать её.

Значение по умолчанию должно принадлежать допустимой области значений свойства. Для фиксированного свойства должно быть задано корректное фиксированное значение через описание значения по умолчанию.

Текстовая форма имеет ограничения совместимости с другими свойствами: она не сочетается с обычными элементными свойствами того же типа как произвольная структура. Формы XML, локальные имена и пространства имён должны образовывать непротиворечивое представление.

### Согласованность фасетов

Ограничения производного типа проверяются совместно с ограничениями базы. Например, нижняя граница длины не может превышать верхнюю, а ограничение максимальной длины не должно расширять допустимую область относительно базового ограничения.

Одного правильного значения отдельного фасета недостаточно. Корректность зависит от применимости к типу, сочетания с другими фасетами и унаследованного контекста. Числовые границы с включением и исключением конца диапазона также должны проверяться как совместная система требований.

### Группы сообщений проверки

Ошибки модели группируются по проверяемому уровню:

| Префикс | Проверяемая часть |
| --- | --- |
| `xdto-model-...` | Фабрика и состав модели. |
| `xdto-package-...` | Пакет и его зависимости. |
| `xdto-valueType-...` | Описание типа значения. |
| `xdto-objectType-...` | Описание объектного типа и свойств. |
| `xdto-facet-...` | Применимость и согласованность фасетов. |

После префикса могут указываться номера раздела и правила, затем текст ошибки. Такая структура помогает отличить ошибку описания типа от ошибки конкретных данных. Исправление сообщения об отсутствии пакета, например, не сводится к заполнению поля экземпляра.

## Модель и преобразование данных

XDTO-пакет описывает, какие данные могут передаваться. Он сам по себе не определяет, как поля объектов конкретной конфигурации заполняют эту модель и как принимаемые значения записываются обратно.

Соответствие между прикладными данными и XDTO-моделью определяется логикой преобразования. XDTO описывает систему типов обмена независимо от структуры хранения данных в конкретной конфигурации.
