# Требования к YAML для генерации XDTO-модели

AsyncAPI YAML описывает контракт сообщений и является исходными данными для генерации XSD. XSD импортируется в 1С как модель XDTO, которую Адаптер Kafka использует при конвертации данных. Требования к YAML должны обеспечивать согласованность трёх представлений: схемы сообщения, модели XDTO и фактических данных JSON.

Этот раздел определяет целевой профиль входного YAML для **произвольного формата** Адаптера Kafka. Унаследованная поддержка стандартного EnterpriseData использует стандартные пакеты соответствующей версии; генерация собственной схемы не воспроизводит стандарт EnterpriseData и не заменяет его пакеты.

Основа требований: [описание AsyncAPI](asyncapi-yaml.md), [модель XDTO](xdto.md) и [поддерживаемая модель XDTO в Адаптере Kafka](adapter-xdto-requirements.md). [Скрипт генерации](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/generator/asyncapi2xsd.py) и [описание его запуска](xsd-generation.md) являются реализацией и эксплуатационной документацией. Требования этого раздела определяют входной контракт и целевую модель данных.

## Область профиля и сохранение контракта

Базовый профиль включает именованные объектные схемы, простые значения, UUID, перечисления, локальные ссылки и табличные коллекции объектных строк. Более широкие возможности AsyncAPI или JSON Schema не означают автоматической поддержки генератором и конвертацией адаптера.

YAML должен описывать **конечное тело сообщения**, а не промежуточную структуру правил КД. Если промежуточные данные преобразуются в табличный объект или группу свойств, описание сообщения должно отражать результат этого преобразования.

Генерация должна сохранять:

- имена полей и их вложенность;
- типы значений и ссылочную семантику UUID;
- обязательность присутствия поля;
- допустимость явного пустого значения;
- количество и порядок элементов коллекций;
- ограничения значений и коды перечислений.

Если требование не представимо в выбранной модели XDTO либо не поддерживается стандартной конвертацией, оно требует отдельного согласованного механизма или явного отказа. Молчаливое ослабление, усиление или удаление ограничения недопустимо. Успешная генерация XML и импорт пакета сами по себе не доказывают соответствие контракту сообщения.

Генератор переносит объявленные `properties`. Отсутствие `additionalProperties` не означает явного запрета неизвестных полей исходной JSON Schema; полная эквивалентность произвольной JSON Schema и XSD не заявляется. `additionalProperties: false` допускается: XSD содержит только объявленные свойства, а проверка default/examples отклоняет неизвестные поля. Открытые словари (true или схема в additionalProperties) не поддерживаются.

### Поддерживаемые формы входа

- Каждая самостоятельная схема имеет явный поддерживаемый простой, объектный тип или массив либо является локальным алиасом. Корневые схемы массивов поддерживаются и создают объектный тип коллекции с полем row.
- Inline вложенный объект получает имя типа `{Родитель}.{Поле}`. Локальная ссылка `$ref` использует имя исходного типа. Явно заданные имена схем сохраняются.
- Массив допускается среди реквизитов: простые items создают повторяющееся простое свойство, объектные items — табличный реквизит. Объект с единственным массивом объектных строк считается явным контейнером. minItems по умолчанию равен 0; обработка пустого источника определяется таблицей профиля ниже.
- `maxItems` отсутствует либо является неотрицательным целым числом не меньше minItems, включая 0 и 1. Простые списки и массивы объектных строк допускаются среди других реквизитов; вложенные массивы не поддерживаются.
- Структурные ограничения рядом с `$ref`, `AdditionalInfo`, boolean enum и пользовательские ограничения UUID не входят в профиль. UUID задаётся `type: string`, `format: uuid` без дополнительных фасетов или enum.

Общие требования к массивам и расширенным схемам ниже описывают их смысл; они не отменяют ограничения поддерживаемых форм входа. Неподдерживаемое требование должно приводить к явному отказу, а не к изменению контракта.

## Разделы YAML, используемые при генерации

**Единственный обязательный раздел для генерации — `components.schemas`.** Он должен быть непустым словарём именованных схем и полностью определять модель данных. Для генерации достаточно YAML следующей структуры:

```yaml
components:
  schemas:
    Product:
      type: object
      properties:
        id:
          type: string
          format: uuid
        name:
          type: string
      required:
        - id
        - name
```

Такой файл содержит входные данные генератора, хотя сам по себе не является полным документом AsyncAPI. Требования полноты спецификации AsyncAPI и требования к входу генератора различаются.

| Раздел или свойство | Обязательность для генерации | Использование |
| --- | --- | --- |
| `components.schemas` | Обязателен. | Определения типов, свойств, ссылок и ограничений. |
| `channels.<канал>.address` | Необязателен. | Адрес топика может использоваться для формирования имени типа соответствующей схемы. |
| Ссылки сообщений канала и `components.messages` | Необязательны. | Вспомогательная связь адреса топика со схемой при именовании по каналу. Не заменяют `components.schemas`. |
| `asyncapi`, `info`, `defaultContentType`, `operations`, остальные разделы | Необязательны. | Не определяют модель XDTO и не являются условием генерации. Их назначение в полной спецификации описано на странице AsyncAPI. |

Отсутствие каналов, сообщений, операций или метаданных документа не должно препятствовать генерации типов из `components.schemas`. Генерация не зависит от того, объявлена ли схема как `payload` сообщения: общие схемы и модели строк также являются источниками типов.

YAML должен быть синтаксически корректным и не содержать дублирующихся ключей. Значения, похожие на логические, числовые или даты, заключаются в кавычки, если должны оставаться строками. Числовые ограничения записываются числами, логические признаки — `true` и `false` без кавычек. Порядок словарей не должен определять выбор сообщения или разрешение ссылки.

## Схемы, сообщения и имена типов

### Источник типов

Каждый ключ `components.schemas` идентифицирует отдельную схему. Схема имеет явный `type`, локальную ссылку либо поддерживаемую конструкцию композиции. Пустое определение не является неявной строкой или автоматически поддерживаемым открытым объектом.

Общие типы, перечисления и модели строк могут существовать без собственного канала. Наличие канала не является условием пригодности схемы для повторного использования.

Для единицы обмена КД требуется объектный тип формата. Корневой массив или примитив может быть корректным телом AsyncAPI, но требует отдельно определённого сценария адаптера. Пакет записей регистра и одиночный объект не должны смешиваться под одним неуточнённым описанием тела.

### Необязательное именование по адресу топика

Если для формирования имени типа используется адрес топика, его связь со схемой может разрешаться по цепочке:

```text
channels.<канал>.messages.<сообщение>.$ref
  → components.messages.<сообщение>.payload.$ref
  → components.schemas.<схема>
```

Для применения такого именования адрес канала и его связь со схемой должны быть определены. Если подходящего канала или разрешаемой связи нет, имя типа формируется из ключа схемы в `components.schemas`; наличие канала не становится обязательным условием. Если канал содержит несколько сообщений, каждое сопоставляется со своей схемой; выбор первого элемента словаря не является правилом. Если реализовано только одно сообщение на канал, остальные варианты должны отклоняться явно.

Одна схема может использоваться в нескольких каналах. Такое повторное использование не должно менять её тип в зависимости от порядка каналов. При именовании по адресу все связи должны давать согласованное имя либо неоднозначность должна быть устранена явным сопоставлением вне схемы данных.

### Имена и пространство имён

Имена схем и полей должны позволять получить допустимые имена XML/XDTO без потери соответствия JSON. В базовом профиле исключаются пробелы, двоеточия, `/` и `~` в именах схем; расширение допустимых имён требует определённого механизма сопоставления и разрешения ссылок.

Имена полей берутся из ключей `properties`, а не из `title` или `description`. Переименование JSON-поля только ради удобства генератора изменяет контракт.

Имена типов должны оставаться уникальными после нормализации, построения имён вложенных типов и применения префикса или суффикса канала. Например, `order-details` и `order_details` не должны незаметно стать одним `OrderDetails`. Служебный тип `UUID` также участвует в проверке коллизий.

URI собственного пакета задаётся согласованным параметром генерации. Он не выводится автоматически из имени топика или `info.version`. Собственный формат не должен использовать URI семейства EnterpriseData: адаптер распознаёт его и включает специальную стандартную обработку.

## Локальные ссылки `$ref`

Ссылка на схему имеет вид `#/components/schemas/<имя>`, заключена в кавычки и разрешается с точным совпадением регистра. При необязательном именовании по каналу ссылки на сообщения имеют область `#/components/messages/<имя>`; она не заменяет область ссылок на схемы.

```yaml
productId:
  $ref: '#/components/schemas/UUID'
```

Повторное использование должно сохранять тип целевой схемы: примитив остаётся типом значения, объект — объектным типом, перечисление — ограниченным типом значения. Алиас переиспользует имя и идентичность целевого типа; циклы алиасов отклоняются. `$ref` не означает, что любая целевая схема является сложным типом.

Ссылка на объектную схему представляет вложенные данные объекта. Она не означает ссылку на сущность 1С. Ссылка на сущность задаётся строкой с `format: uuid` непосредственно или через переиспользуемую UUID-схему.

В базовом профиле рядом с `$ref` допускаются описательные аннотации. Дополнительные структурные ограничения отклоняются. Ограничение одного места использования не должно изменять общее определение для остальных полей.

Внешние файлы, URL и ссылки на произвольные вложенные фрагменты требуют отдельного профиля разрешения. Неизвестная ссылка является ошибкой. Циклические ссылки допустимы только при поддержке генератором и конечной модели экземпляра; обязательный цикл вложенных объектов без возможности завершения не описывает конечное сообщение.

## Типы значений

| YAML | Целевой тип | Требование |
| --- | --- | --- |
| `type: string` | `xs:string` | Не получает ссылочную семантику только из имени поля. |
| `type: string`, `format: uuid` | Собственный `tns:UUID` | Сохраняет распознаваемый адаптером UUID-тип. |
| `type: string`, `format: date-time` | `xs:dateTime` | Представление даты-времени должно быть согласовано с сообщениями и правилами. |
| `type: string`, `format: date` | `xs:date` | Дата, а не строка произвольного формата. |
| `type: string`, `format: time` | `xs:time` | Время в согласованном представлении. |
| `type: integer` | `xs:integer` | Не вводится неявный предел 32 или 64 бит. |
| `type: integer`, `format: int32` | `xs:int` | Явно задан диапазон 32-разрядного целого. |
| `type: integer`, `format: int64` | `xs:long` | Явно задан диапазон 64-разрядного целого. |
| `type: number` | `xs:decimal` | Десятичное представление; точность значимых данных согласована. |
| `type: number`, `format: float` / `double` | `xs:float` / `xs:double` | Приближённое представление выбрано явно. |
| `type: boolean` | `xs:boolean` | Передаются логические значения, а не строки `"true"` и `"false"`. |

`format` уточняет совместимый базовый `type` и не заменяет его. `type: uuid`, `type: date` и имена платформенных типов 1С не используются. Неизвестный формат с существенной семантикой требует отдельной поддержки; превращение его в обычную строку не считается сохранением требований.

Диапазон XSD-типа не гарантирует точную обработку всех его значений числами 1С и внешним потребителем JSON. Формат должен ограничивать данные реально согласованным диапазоном и точностью, особенно для больших целых, денег и вычисляемых величин.

## UUID и ссылки на сущности

```yaml
UUID:
  type: string
  format: uuid

Product:
  type: object
  properties:
    id:
      $ref: '#/components/schemas/UUID'
  required:
    - id
```

UUID-поля собственного формата должны приводить к простому типу с именем `UUID`, распознаваемым адаптером без учёта регистра. Схема с иным исходным именем может использовать `format: uuid`, но результирующий тип поля должен сохранять это соглашение.

Строка длиной 36 символов, имя поля `ref` или тип `CustomerId` без согласованного UUID-преобразования не заменяют тип `UUID`. Типы на основе `Ref` относятся к EnterpriseData и не являются механизмом ссылок этого профиля.

Назначение UUID определяется описанием поля и правилами: идентификатор самой сущности, ссылка на товар, владельца строки или другой объект. Общий UUID-тип не определяет справочник для поиска. Для идентификации объекта правила должны связывать его ссылку конфигурации с соответствующим полем формата.

`x-topics` рекомендуется для документирования адресов топиков связанных сущностей:

```yaml
productId:
  type: string
  format: uuid
  x-topics:
    - 'catalog.products.changed'
```

Это необязательная аннотация. Она не является `$ref`, не меняет строковое значение, не создаёт ПКО и не определяет алгоритм поиска. Отсутствие `x-topics` не препятствует генерации UUID-типа.

## Объекты и обязательность

Для всех полей nullable вычисляется из отсутствия поля в `required` непосредственного родителя: поле вне `required` допускает `null`, поле в `required` — не допускает `null`. Правило применяется к простым значениям, вложенным объектам и массивам, включая поля по локальной ссылке `$ref`. Допустимость `null` и нижняя граница `minOccurs` — разные характеристики.

У массивов есть особенности: количество элементов задаётся `minItems` и `maxItems`; отсутствующий `minItems` принимается равным `0`. Это относится к простым спискам, массивам объектов и массивам по локальной ссылке `$ref`. Следующая таблица описывает обработку пустого источника с учётом этих границ.

| Поле включено в `required` | `minItems` | Пустой источник |
| --- | --- | --- |
| Нет | 0 | Поле со значением `null`. |
| Нет | >0 | Nullable отключается с предупреждением; недостаточное количество элементов является ошибкой. |
| Да | 0 | Поле со значением `[]`. |
| Да | >0 | Недостаточное количество элементов является ошибкой. |

Заполненный массив проверяется по `minItems`, `maxItems` и ограничениям каждого элемента. Nullable коллекции не разрешает null её элементов. При положительном минимуме XSD не содержит nillable=true для поля массива. Предупреждение содержит категорию `[array-nullable]`, путь YAML и минимальное количество элементов.

Профиль описывает полное состояние объекта: пустые поля массива не должны пропускаться. Скрипт генерирует XSD и проверяет default/examples, но не создаёт JSON и не заполняет отсутствующие поля. Нормализация пустого источника в null или [] и обязательный выпуск поля являются требованиями к сериализации адаптера, а не автоматически реализованным поведением XSD.

В XML простой список остаётся повторяющимся элементом: minOccurs соответствует minItems, maxOccurs — maxItems либо unbounded. При minItems=0 XML допускает отсутствие элементов; nillable относится к отдельному элементу и не обеспечивает null всего списка. Для массива объектов среди нескольких реквизитов контейнер имеет minOccurs=1; количество его row определяется minItems/maxItems. Значения атрибутов, совпадающие со стандартными значениями XSD, не записываются.

Для остальных типов прежние правила сохраняются: поле вне required допускает null независимо от минимальной границы; обязательное поле с нулевой границей может быть пропущено. Отсутствующий minLength или minimum используется как 1 для расчёта присутствия, без добавления отсутствующих фасетов типа. Это правило не распространяется на minItems.

## Вложенные объекты и специальные группы

Вложенный `type: object` или `$ref` на объект должен соответствовать поддерживаемому механизму адаптера в обоих направлениях. Произвольное имя многополевого типа само по себе не гарантирует чтение всех его полей: объект может попасть в обработку составного значения, где выбирается первое установленное свойство.

Составное значение, содержащее варианты, и обычная группа полей являются разными моделями. Если выбран механизм составного значения, контракт должен однозначно задавать один вариант. Несколько заполненных вариантов не должны трактоваться как гарантированно сохраняемая обычная структура.

Имя `AdditionalInfo` зарезервировано поведением адаптера для специальной XDTO-сериализации дополнительных данных. Оно не используется для несвязанного обычного вложенного объекта без согласования этой обработки. Открытая схема или `additionalProperties` не заменяет данный механизм.

## Коллекции и таблицы

### Общие требования к массиву

`type: array` содержит одну схему элемента в `items`. Кортежи, разные схемы элементов по позиции и неопределённый тип элемента не входят в базовый профиль.

`minItems` и `maxItems` — неотрицательные целые числа, а не логические значения. Нижняя граница не превышает верхнюю. Отсутствие `minItems` допускает ноль элементов; отсутствие `maxItems` не задаёт верхнего ограничения.

В стандартной схеме required определяет допустимость отсутствия поля; целевой профиль полной выгрузки требует выпускать все поля массива и использует required для вычисления nullable. Длина присутствующего массива определяется minItems/maxItems. Обязательный массив с `minItems: 0` может быть пустым; `maxItems: 0` допускает только пустой массив и само по себе не противоречит обязательности. Генератор не должен автоматически заменять нижнюю границу на `1`.

Обязательность массива, допустимость `null` вместо массива и допустимость пустых элементов — три разных требования. `nillable` повторяющегося XDTO-свойства относится к отдельному элементу, а не ко всему массиву.

### Таблица объектных строк

В XDTO таблица использует служебный объект-контейнер с ровно одним повторяющимся свойством строк. В JSON контейнер разворачивается в массив объектов; имя свойства строк не передаётся. YAML конечного тела описывает массив:

```yaml
OrderLines:
  type: array
  minItems: 0
  items:
    $ref: '#/components/schemas/OrderLine'

OrderLine:
  type: object
  properties:
    productId:
      type: string
      format: uuid
    quantity:
      type: number
  required:
    - productId
    - quantity
```

Генератор представляет `OrderLines` объектным типом XSD с повторяющимся свойством `row` типа `OrderLine`. Это служебное представление массива. В конечном теле сообщения:

```json
{"lines": [{"productId": "11111111-1111-1111-1111-111111111111", "quantity": 1}]}
```

Сериализация адаптера разворачивает все распознанные таблицы, включая корневые и вложенные, в массивы. Если исходная YAML-модель явно описывает объект с единственным повторяющимся свойством строк, генератор сохраняет этот контейнер в XSD, но адаптер также разворачивает его. Такая объектная YAML-модель не описывает итоговую форму JSON; контракт сообщения должен задавать массив. Имя `row` или `Строка` не служит признаком таблицы: используется структура типа XDTO.

Имя строк может отличаться от `row`, но объект таблицы сохраняет единственное повторяющееся свойство. Добавление в обёртку второго поля, например `total`, меняет классификацию адаптером. Контекст и агрегаты располагаются вне табличной обёртки.

Границы массива строк переходят в границы повторяющегося свойства. При `maxItems: 1` верхняя граница XDTO становится `1`, и тип больше не распознаётся как стандартная таблица. Генератор поддерживает границы 0 и 1 и сохраняет их точно, не увеличивая ради классификации таблицы. При проверке default/examples признак массива хранится отдельно от верхней границы. Распознавание и конвертация такого типа на платформе определяются моделью адаптера, а не фактом компиляции XSD.

Обязательность самой таблицы задаётся у родителя отдельно от количества строк. Если требуется различать отсутствующее поле строк и присутствующий пустой массив, должна быть определена сохраняющая это различие модель: прямое повторяющееся XSD-свойство с нулём значений не предоставляет отдельного XML-элемента для обозначения пустого массива.

### Табличный массив среди реквизитов

Поле `type: array` с объектными items допускается рядом с обычными properties. В XSD ему соответствует одиночное свойство объектного типа таблицы `{Родитель}.{Поле}` с единственным повторяющимся свойством `row`. Inline тип строки — `{Родитель}.{Поле}.Row`; общий тип по ссылке переиспользуется.

В целевом JSON поле таблицы присутствует независимо от required; required определяет nullable с учётом minItems по таблице профиля. Обязательное `lines` с minItems=1/maxItems=100 требует таблицу и от 1 до 100 строк; обязательное поле с minItems=0 допускает пустую таблицу. В YAML и JSON поле сохраняет форму массива строк, а не объекта с row.

Объект с единственным свойством-массивом объектных строк считается уже явным контейнером: дополнительная обёртка не создаётся, имя строк берётся из properties. Для этого повторяющегося свойства применяется описанная выше логика required/min; прежнего запрета несогласованных сочетаний нет. Для простого списка действует та же проверка: отсутствие и присутствующий пустой список неразличимы на уровне повторяющихся XML-элементов.

### Массивы простых значений

Массив простых значений создаёт непосредственно повторяющееся свойство простого типа без табличной обёртки. Ограничения items, включая enum и локальную ссылку на простой тип, применяются к каждому элементу. При отсутствии minItems нижняя граница равна 0. Nullable разрешён только для поля вне required с нулевым минимумом. Например, fixedTags с minItems=1/maxItems=3 имеет границы 1..3 и не допускает null.

Для прямого списка схема элемента определяет простой тип, а границы количества — повторяемость свойства. При верхней границе `1` модель становится одиночным свойством, что требует отдельного решения для сохранения JSON-массива.

Отсутствующий массив и присутствующий пустой массив могут не различаться в прямом повторяющемся XSD-представлении. Если это различие существенно для контракта, необходима согласованная модель контейнера и поддержка конвертации либо явный отказ от неподдерживаемой формы.

При отправке пустые элементы не обязательно отбрасываются: адаптер может добавлять `Неопределено` в список. Поэтому схема элемента и политика пустых значений должны быть согласованы. Поддержка отправки простого списка не доказывает симметричную поддержку всех вариантов получения.

### Самостоятельная строка

Для обмена одной строкой табличной части схема описывает самостоятельный объект, например `OrderLineEvent`, а не массив или табличную обёртку. Она содержит контекст владельца, идентификацию строки и необходимые реквизиты. UUID владельца, номер строки и устойчивый идентификатор строки имеют разные назначения.

Наличие такой схемы не создаёт регистрацию изменений строки, поиск владельца или алгоритм обновления табличной части. Эти задачи относятся к правилам и настройкам обмена.

## Перечисления

`enum` — непустой список различных кодов, соответствующих явному типу и остальным ограничениям схемы. Строки и числа не смешиваются; строковые коды, похожие на числа или логические значения, записываются в кавычках.

```yaml
OrderStatus:
  type: string
  enum:
    - 'new'
    - 'confirmed'
  x-enumNames:
    - 'Новый'
    - 'Подтверждён'
```

Каждый код должен сохраняться фасетом перечисления целевого типа. Генератор не должен заменять ограниченный enum обычным базовым типом. Это относится к отдельной схеме, полю и элементу массива.

`x-enumNames` рекомендуется для расшифровки кодов и является необязательным. Если задано, число и порядок подписей соответствуют `enum`. Подписи не заменяют коды обмена и не создают правила конвертации перечислений конфигурации.

Числовой enum требует сохранения числового типа и согласованной обратной конвертации. Enum с единственным логическим значением не эквивалентен обычному булевому типу с двумя значениями; неподдерживаемая форма должна отклоняться явно.

## Ограничения значений

| Свойство | Требование к YAML и преобразованию |
| --- | --- |
| `minLength`, `maxLength` | Неотрицательные целые границы длины строки; нижняя не превышает верхнюю. Сохраняются соответствующими фасетами. |
| `pattern` | Строковое выражение с определённой представимостью в диалекте XSD. Неподдерживаемый синтаксис не переносится механически. |
| `minimum`, `maximum` | Числовые включительные границы для числового типа. |
| `exclusiveMinimum`, `exclusiveMaximum` | Исключительные границы в синтаксисе выбранного диалекта схемы; не смешиваются числовая и устаревшая логическая формы. |
| `multipleOf` | Положительный шаг, сохраняемый точно либо отклоняемый как неподдерживаемый. |
| `default` | Значение соответствует типу, enum и всем ограничениям. Является аннотацией, не командой заполнения. |

Ограничения совместимы с базовым типом и форматом. Например, границы чисел не заменяют ограничения строкового UUID. Пустой диапазон, противоречащие границы и невозможное значение по умолчанию должны выявляться до успешной генерации.

Диалекты регулярных выражений JSON Schema и XSD различаются. Особого решения требуют якоря `^` и `$`, классы, группы и другие конструкции; одинаковый текст не гарантирует одинаковую проверку. Подробнее о целевом диалекте: [XML Schema Datatypes: pattern](https://www.w3.org/TR/xmlschema-2/#rf-pattern).

Переносимый профиль включает ASCII-литералы, положительные ASCII-классы и диапазоны, `\d`, экранированные специальные символы и обычные повторения. Например, `[A-Z]{2}` проверяет наличие двух последовательных заглавных ASCII-букв, а не полное совпадение строки: генератор сохраняет поиск подстроки в XSD. Wildcard `.`, группы, альтернативы, lookaround, backreference и ленивые повторения отклоняются. Для UUID используется отдельный тип с фиксированной длиной и шаблоном, а не пользовательский `pattern`.

Для десятичного числа шаг `0.01` может соответствовать ограничению дробных знаков. Шаг `0.05` не эквивалентен двум знакам после запятой. Для `float` и `double` нельзя считать десятичный фасет универсальным способом точного сохранения шага.

Значения `default` и `examples` должны соответствовать типу и ограничениям схемы; генератор проверяет их как значения модели. `default` не записывается как default/fixed XSD, не делает поле обязательным и не выполняет заполнение. Для фактического заполнения используются правила конвертации. Примеры и значения по умолчанию допускаются на массивном свойстве в исходной JSON-форме списка. Проверяются типы элементов, их ограничения и количество. В примере родительского объекта табличный реквизит также задаётся массивом, без искусственного поля row.

## Композиция и расширенные конструкции

`allOf`, `oneOf` и `anyOf` корректны только в рамках определённого профиля их преобразования. В базовом профиле без такой поддержки они отклоняются с указанием пути схемы.

`allOf` означает одновременное применение требований. Его преобразование требует согласования типов общих полей, пересечения ограничений и объединения требований обязательности. Простое копирование `properties` последнего элемента теряет контракт.

`oneOf` и `anyOf` описывают альтернативы. Они не превращаются автоматически в обычный объект со всеми полями или в составное значение КД. Связь с механизмом выбора варианта адаптера должна быть определена отдельно.

Также требуют отдельной поддержки: условные схемы, `not`, `const`, `uniqueItems`, кортежи, словари произвольных ключей, `additionalProperties=true`, `additionalProperties` со схемой, `patternProperties` и иные проверки вне базового профиля. Отсутствие `additionalProperties` в YAML нельзя выдавать за явно заданный `additionalProperties: false`. Ограничение открытости исходной схемы и поведение объектной модели должны быть согласованы без молчаливого изменения.

Расширение профиля должно определять синтаксис YAML, целевую модель XDTO, поведение конвертации и условия отказа. Корректность общей JSON Schema не заменяет эти четыре условия.

## Описательные свойства и расширения x-*

`title` и `description` раскрывают назначение схемы и поля. Для идентификаторов, ссылок, дат, количеств и кодов в описании указываются необходимые бизнес-соглашения. Текст не заменяет машинные ограничения или правила КД.

`deprecated` отмечает устаревание, но не удаляет поле, не отменяет обязательность и не меняет тип.

`x-*` — дополнительные метаданные документа. `x-last-modified` может описывать дату и автора изменения; `x-enumNames` — подписи enum; `x-topics` — связанные топики. Эти свойства не становятся полями сообщения, если отдельно не объявлены в `properties` как реальные данные.

Рекомендуемые расширения необязательны. Неизвестная описательная аннотация не меняет тип или ограничения. Если расширение используется как машинная команда генератору, его семантика должна быть отдельно документирована; нельзя приписывать такое значение произвольному `x-*`.

## Проверяемые критерии соответствия

YAML пригоден для выбранного профиля, если:

- `components.schemas` содержит однозначные определения, ссылки разрешаются, коллизий результирующих типов нет;
- тело сообщения описано в конечной форме: таблицы представлены массивами строк без служебных контейнеров XDTO;
- ссылка UUID отличается от вложенного объекта, обычной строки и ссылки EnterpriseData;
- вложенные группы и варианты соответствуют механизмам адаптера;
- обязательность, допустимость `null`, непустота и количество значений описаны независимо;
- все ограничения имеют точное правило представления либо вызывают явный отказ;
- примеры соответствуют схеме и согласованной политике пустых значений;
- поддержка отправки и получения заявлена только для согласованных моделей.

Примеры данных в YAML должны раскрывать допустимые состояния контракта: отсутствие необязательного поля, пустую строку, значимый ноль и `false`, пустой массив, граничное количество элементов, UUID, enum, табличный объект и вложенную группу. Для расширенного профиля с допустимым `null` отдельно описываются явное пустое значение и отсутствие поля. Каждый пример должен соответствовать ограничениям своей схемы и согласованной семантике конвертации.

## Массивы, группы и аннотации формата

Корневой массив и общая схема массива по $ref создают объектный тип коллекции с повторяющимся полем `row`. Исходное значение в YAML default/examples остаётся списком; при проверке оно переводится в XML коллекции. Скалярное поле, ссылающееся на такую схему, также принимает список. Границы 0 и 1 поддерживаются; неизвестные поля в примерах объектов отклоняются.

Начальный `^` и конечный `$` в pattern переводятся в ограничения начала и конца строки, сохраняя семантику поиска при отсутствии якорей. Конечный `$` требует конца входной строки, без режима multiline; завершающий перевод строки не игнорируется. Семантика якорей соответствует [ECMAScript CompileAssertion](https://tc39.es/ecma262/2024/multipage/text-processing.html#sec-compileassertion). Остальные ограничения переносимого regex-профиля сохраняются.

`format: email` поддерживается как [аннотация формата JSON Schema](https://json-schema.org/draft/2020-12/json-schema-validation#name-format-annotation-vocabular) строки и сохраняется в xs:documentation. Он не превращается в приближённый regex или неизвестный тип. minLength/maxLength/pattern и enum строки проверяются; полная проверка адреса электронной почты форматом email в XSD не выполняется. Неизвестные форматы продолжают вызывать ошибку.

### Запись значений по умолчанию XSD

Атрибут не записывается, если его вычисленное значение совпадает со стандартным значением XSD: minOccurs=1, maxOccurs=1, nillable=false, attributeFormDefault=unqualified. Отличающиеся значения сохраняются явно, например minOccurs=0, maxOccurs=unbounded, nillable=true и elementFormDefault=qualified. Это сокращение записи не меняет модель; сначала вычисляются свойства с приоритетами исходного YAML, затем сравниваются со значениями по умолчанию целевого XSD.
