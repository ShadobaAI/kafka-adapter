## Хранение исходников

Исходный код хранится в **EDT-формате** (каталог `src/`). Для локальной работы:

1. Клонируйте [репозиторий адаптера](https://github.com/ShadobaAI/kafka-adapter).
2. Клонируйте [базовый проект](https://github.com/ShadobaAI/kafka-adapter-base).
3. Откройте оба проекта в EDT.
4. Базовый проект — информационная база для тестирования.
5. Адаптер — на поддержке библиотеки / как часть основной конфигурации / как расширение.

## Сборка и тестирование через CI

Release workflows и `.github/scripts/create_test_dt.py` используют Vanessa Runner 3.x (OneScript 2.0.0+). Образы `ibcmd` и `client` должны содержать эту версию Runner.

Тестовая и демонстрационная ИБ создаются из DT-шаблона командой `vrunner infobase init --src <шаблон.dt>`, затем CF/XML загружается через `vrunner cf load`, а расширения — через `vrunner cfe load`. Команды `load` обновляют конфигурацию БД автоматически; параметры указываются до позиционного пути источника. Unit-тесты и заполнение ИБ запускаются через `vrunner run enterprise`.

При ошибке unit-запуска или отсутствии `exit-code.txt` скрипт выводит код завершения Vanessa Runner, `vrunner.log` и `unit.log` в лог job. Workflow сохраняет эти файлы вместе с логами Coverage41C и dbgs в артефакте `unit-test-diagnostics`, в том числе при падении тестов. Отсутствие `exit-code.txt` означает, что ожидаемый статус тестов не получен; причину нужно определять по диагностическим логам.

Скрипты заполнения ИБ и unit-запуска изменяют положение и размер только видимых окон `1cv8c`; принудительное открытие скрытых служебных окон через `windowmap` может перекрыть интерфейс и остановить запуск клиента.

Локальный прогон на платформе 8.5.1.1529 с YAxUnit 25.12 выявил аварийное завершение `ibsrv` с `Операция не поддерживается: clientlessMode` при тесте `Пауза(). Сообщает о запрете паузы в клиент-серверном вызове`. Ошибка воспроизводится и без Runner/Coverage41C; исправление Docker-зависимостей само по себе не обеспечивает прохождение всего набора тестов в этом runtime.

## Публикация отчётов CI

Release workflow публикует страницу Reports для запуска даже при аварийном завершении тестов. Ссылка появляется в Summary job публикации и в описании релиза. Доступные отчёты Allure и SonarQube публикуются независимо; для отсутствующих отчётов отображается сообщение со ссылкой на логи и артефакты CI. Отсутствие отчёта не означает успешное выполнение тестов.

Статический отчёт SonarQube формируется только после успешной отправки текущего анализа и завершения его фоновой обработки со статусом `SUCCESS`. Scanner использует `.scannerwork` в рабочем каталоге проекта, в том числе при запуске через Docker. Если `report-task.txt` или `ceTaskUrl` отсутствует, обработка завершается ошибкой или превышает время ожидания, новый отчёт SonarQube не публикуется.

Релизы с `prerelease: true` анализируются в Sonar-проекте `kafka-adapter-prerelease`, stable-релизы — в `kafka-adapter`; в обоих случаях `sonar.projectVersion` равен тегу релиза. Отчёт и ссылка на dashboard используют выбранный проект. Prerelease запускает pipeline по событию `published`, stable — по `released`, включая перевод опубликованного prerelease в stable. Stable-событие `published` пропускается, чтобы избежать второй сборки. Sonar jobs одного канала выполняются последовательно без автоматической отмены текущего job.

Перед анализом любого канала CI получает GitHub Releases и выбирает последний опубликованный stable по `published_at`, исключая draft, prerelease и текущий тег. Версии в workflow и проверке не фиксируются. При отсутствии или неоднозначности stable-базы CI завершается ошибкой. Затем проверяются существование выбранного Sonar-проекта и `Specific analysis` основной ветки: analysisId должен принадлежать этому проекту, версия анализа — совпадать с выбранным stable-тегом, а `revision` — с commit этого тега. Отсутствующая, удалённая или неверная база блокирует scanner и публикацию нового Sonar-отчёта.

Генератор разрешает `Specific analysis` по analysisId во всей постраничной истории проекта и отображает версию, дату и ключ базового анализа. Отсутствующая база или её версия считаются ошибкой сбора отчёта.

Создание проекта само по себе не переносит production-анализы, настройки, issues или hotspot reviews. Автоматическая инициализация и переключение production-базы пока не реализованы: до запуска CI нужно создать соответствующий анализ и настроить `Specific analysis`. Свежий анализ stable-исходников задаёт базу по новой дате и не гарантирует точное сравнение production-версий; фактический период New Code требует отдельной проверки. Release workflow исполняется из commit тега, поэтому перевод уже существующего prerelease в stable не гарантирует применение доработок, находящихся только в текущей ветке.

Локальная проверка production-базы и разрешения analysisId: `python -B -m unittest discover -s .github/scripts -p test_sonar_release_baseline.py -v`.
