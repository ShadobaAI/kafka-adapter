# Окружение

Требования к окружению для разработки и тестирования самой подсистемы адаптера.

## Обязательные компоненты

| Компонент | Версия | Назначение |
|-----------|--------|-----------|
| **1С:Предприятие** | 8.3.26+ | Платформа запуска |
| **Режим совместимости** | 8.3.21 | Режим совместимости конфигурации и расширения |
| **glibc** | 2.28+ | Обязательная зависимость на Linux; на старых дистрибутивах возможны проблемы с запуском внешней компоненты |
| **1C:Enterprise Development Tools (EDT)** | 2025.2+ | IDE для разработки |
| **Apache Kafka** | 3.7+ | Брокер сообщений для тестовой среды |
| **[Simple Kafka Connector 1C](https://github.com/NuclearAPK/Simple-Kafka_Adapter)** | 1.9.2+ | Внешняя компонента для работы с Kafka; встроена в подсистему и обновляется вместе с ней. Отдельная установка и регистрация не требуются |

## Хранение исходников

Исходный код хранится в **EDT-формате** (каталог `src/`). Для локальной работы:

1. Клонируйте [репозиторий адаптера](https://github.com/ShadobaAI/kafka-adapter).
2. Клонируйте [базовый проект](https://github.com/ShadobaAI/kafka-adapter-base).
3. Откройте оба проекта в EDT.
4. Базовый проект — информационная база для тестирования.
5. Адаптер — на поддержке библиотеки / как часть основной конфигурации / как расширение.

## Сборка и тестирование через CI

Тег релиза содержит версию в формате `X.X.X.X` и может включать суффикс после дефиса. При сборке CF и CFE версия для 1С определяется по части тега до первого дефиса и проверяется на наличие ровно четырёх числовых компонентов, разделённых точками. Неверный формат версии блокирует сборку. Для публикации артефактов и `sonar.projectVersion` используется полный тег релиза, включая суффикс.

Release workflows и `.github/scripts/create_test_dt.py` используют Vanessa Runner 3.x (OneScript 2.0.0+). Образы `ibcmd` и `client` должны содержать эту версию Runner.

Тестовая и демонстрационная ИБ создаются из DT-шаблона командой `vrunner infobase init --src <шаблон.dt>`, затем CF/XML загружается через `vrunner cf load`, а расширения — через `vrunner cfe load`. Команды `load` обновляют конфигурацию БД автоматически; параметры указываются до позиционного пути источника. Unit-тесты и заполнение ИБ запускаются через `vrunner run enterprise`.

Вспомогательный `create_test_dt.py` собирает общий XML только из base и adapter. Параметр `--examples` принимает ZIP XML-выгрузки расширения примеров: оно загружается отдельно как `ТестированиеАдаптераKafka`. Подготовка XML и проверка архива примеров выполняются до удаления существующей тестовой ИБ; после начала её пересоздания сбой Runner не восстанавливает прежнюю базу. Путь ИБ не может совпадать с рабочим каталогом или содержать его, пересекаться с `config-xml` либо содержать входные файлы и builder; входные файлы и builder также не могут находиться в `config-xml`. Такие пути отклоняются до сборки и удаления. Повторная публикация demo DT заменяет существующий release asset через `--clobber`.

### Покрытие и диагностика

Образ `client` должен содержать Coverage41C, Java, `dbgs` и библиотеки EDT `com._1c.g5.v8.dt.debug.core_*.jar`, `com._1c.g5.v8.dt.debug.model_*.jar` в каталоге `EDT_LOCATION`. Vanessa Runner должен поддерживать `--ibsrv-attach` и `--ibsrv-port`.

Unit- и UI-тесты используют `ibsrv` на порту `8314` с именем ИБ `DefAlias`. Клиент и сервер подключаются к общему серверу отладки `http://127.0.0.1:1550`; `dbgs` и Coverage41C запускаются до `ibsrv`. Исходники для замера передаются через `COVERAGE_PROJECT_DIR` или `COVERAGE_SOURCE_DIR`.

Coverage41C получает исходники адаптера для замера покрытия. Quality и SonarQube принимают отчёты Generic Coverage XML версии 1 с непустыми путями файлов, положительными уникальными номерами строк и хотя бы одной строкой с `covered=true`. Проверка XML не сверяет принадлежность пути адаптеру и номера строк с исходниками. Пустой, повреждённый или полностью нулевой отчёт завершает соответствующий job ошибкой. Порог процента покрытия не установлен.

Логи и `exit-code.txt` сохраняются при любом исходе запуска в артефактах `unit-test-diagnostics` и `ui-test-diagnostics`. Они включают вывод клиента или Runner, `ibsrv.log`, `coverage41c.log` и `dbgs.log`. Отсутствие `exit-code.txt` означает, что статус тестов не получен.

## Публикация отчётов CI

Последний опубликованный запуск: [все отчёты](https://shadobaai.github.io/kafka-adapter-tests-reports/latest/), [Allure Unit](https://shadobaai.github.io/kafka-adapter-tests-reports/latest/allure-unit/), [Allure UI](https://shadobaai.github.io/kafka-adapter-tests-reports/latest/allure-ui/) и [SonarQube](https://shadobaai.github.io/kafka-adapter-tests-reports/latest/sonar/).

Release workflow публикует страницу Reports для запуска даже при аварийном завершении тестов. Ссылка появляется в Summary job публикации и в описании релиза. Доступные отчёты Allure и SonarQube публикуются независимо; для отсутствующих отчётов отображается сообщение со ссылкой на логи и артефакты CI. Отсутствие отчёта не означает успешное выполнение тестов.

Подготовка и генерация Allure unit/UI выполняются отдельными шагами: повреждённые результаты одного контура не блокируют отчёт другого, а ошибка сохраняет статус failure. Публикация в `kafka-adapter-tests-reports/main` выполняется в общей concurrency group от начала job, включая checkout и push, без отмены текущего job и с `queue: max` (до 100 ожидающих jobs). Это сериализует публикации из данного репозитория; внешние записи в хранилище отчётов этой очередью не защищены. `latest` содержит отчёты последнего завершившего публикацию запуска.

Статический отчёт SonarQube формируется только после успешной отправки текущего анализа и завершения его фоновой обработки со статусом `SUCCESS`. CI заранее создаёт `.scannerwork` в рабочем каталоге проекта и задаёт `sonar.scanner.metadataFilePath` абсолютным путём: `${PWD}/.scannerwork/report-task.txt` для локального scanner, `${GITHUB_WORKSPACE}/.scannerwork/report-task.txt` при Docker `--volumes-from`, `/usr/src/.scannerwork/report-task.txt` при bind mount. Metadata сохраняется в смонтированном workspace независимо от рабочего каталога scanner (Docker-образ может использовать `/tmp/.scannerwork`) и остаётся доступной после удаления контейнера. Если `report-task.txt` или `ceTaskUrl` отсутствует, обработка завершается ошибкой или превышает время ожидания, новый отчёт SonarQube не публикуется.

Отсутствующие числовые метрики остаются неизвестными и не учитываются как нули в агрегатах покрытия. Для `Specific analysis` карточка baseline показывает версию и дату анализа, разрешённого по analysisId, а не сам UUID.

Каждой Git-ветке соответствует отдельный Sonar-проект. Для `main` сохраняется `sonar.projectKey=kafka-adapter` с существующей историей; для остальных веток ключ имеет вид `kafka-adapter:<ветка>` (`kafka-adapter:prerelease`, `kafka-adapter:develop`). Префикс равен имени репозитория. Ветка берётся из `github.event.release.target_commitish`, независимо от признака `prerelease`. В суффиксе недопустимые символы кодируются как UTF-8 URL-encoding с заменой `%` на `:`: `feature/report` → `kafka-adapter:feature:2Freport`. Кодирование сохраняет различие имён веток, включая `/`, `%`, Unicode и регистр; простая замена `/` на `-` не используется. Если полученный ключ превышает лимит Sonar в 400 символов, используется `kafka-adapter::sha256:<SHA-256 UTF-8 имени ветки>`; двойное двоеточие отделяет эти ключи от обычного кодирования.

`target_commitish` должен содержать имя существующей Git-ветки; SHA commit или отсутствующая ветка блокируют Sonar job. Исходники берутся из commit тега релиза, `sonar.projectVersion` — из `github.event.release.tag_name`. Scanner, отчёт и dashboard используют один выбранный projectKey. `sonar.branch.name` и `--branch` генератора не передаются: анализируется основная Sonar-ветка выбранного проекта, что поддерживается Community Build. `sonar.projectName` и `sonar.working.directory` не задаются; путь metadata задаётся отдельно от рабочего каталога scanner.

Prerelease запускает pipeline по событию `published`, stable — по `released`, включая перевод опубликованного prerelease в stable. Stable-событие `published` пропускается, чтобы избежать второй сборки. Sonar jobs одной Git-ветки выполняются последовательно без автоматической отмены текущего job; разные ветки имеют независимые очереди, кроме имён, различающихся только регистром: GitHub сравнивает concurrency group без учёта регистра.

Каждый проект Git-ветки имеет собственные настройки New Code, Quality Gate, Quality Profiles и историю. Для последовательного анализа версий используется `Previous version`: Sonar рассчитывает период New Code по истории выбранного проекта и версиям, переданным в `sonar.projectVersion`. CI не требует `Specific analysis`, не меняет настройки New Code и не проверяет baseline другого проекта. Признак stable/prerelease GitHub не участвует в выборе периода New Code; при смене release tag база рассчитывается Sonar заново и не закрепляется на последнем stable.

Новые проекты создаются scanner при первом анализе с настройками и permission template сервера. Secret `SONAR_TOKEN` должен содержать user token с правами `Create Projects`, `Execute Analysis`, `Browse` и `See Source Code` выбранных проектов. Permission template новых проектов должна сохранять необходимые проектные права этому пользователю; project analysis token, ограниченный одним проектом, для этой схемы не подходит. История и настройки других проектов автоматически не копируются. Генератор использует фактический период New Code выбранного проекта; для `Previous version` версия baseline берётся из ответа Sonar, а соответствующий анализ — из истории этого же проекта. Если в новом проекте нет предыдущей версии, отчёт не подменяет её историей другого проекта.

Release workflow исполняется из commit тега, поэтому повторный запуск старого release не применяет изменения, находящиеся только в текущей ветке.

Локальные проверки CI helpers: `python -B -m unittest discover -s .github/scripts -p 'test_*.py' -v`. Проверка данных и карточки статического отчёта: `node --test .github/scripts/test_sonar_report.js`.
