# Генерация XSD из YAML

`asyncapi2xsd.py` преобразует схемы данных из YAML в XSD для импорта в XDTO-пакет 1С. Полученная модель используется Адаптером Kafka при конвертации данных через КД 3.1. YAML описывает контракт JSON-сообщений, XSD — его модель типов; использование XSD не меняет формат сообщений Kafka на XML.

Этот раздел описывает переработанную версию скрипта и её поддерживаемый профиль. Контракт входных данных определён в разделе [Требования к YAML для генерации XDTO-модели](yaml-requirements-for-xdto.md). Проверка генератора и XSD не заменяет интеграционную проверку обмена в 1С.

Генератор предназначен для произвольного формата адаптера. Стандартный EnterpriseData использует пакеты соответствующей версии и унаследованный механизм конвертации; скрипт не создаёт замену стандартному EnterpriseData.

## Входные данные и результат

Обязательный источник модели — непустой словарь `components.schemas`. Каждая схема определяет тип, его свойства, ссылки и ограничения. Для генерации не требуется полный документ AsyncAPI: `asyncapi`, `info`, сообщения, каналы и операции могут отсутствовать.

`channels.<канал>.address` используется необязательно для формирования имени типа. Сообщения и их `payload` могут служить вспомогательной связью адреса со схемой. Их отсутствие не препятствует обработке `components.schemas`.

Результат — XSD-файл с согласованными определениями типов выбранного пространства имён. Скрипт обрабатывает схемы из `components.schemas`, включая общие типы, перечисления и модели строк, не связанные с отдельным топиком.

Скрипт не импортирует пакет в 1С и не создаёт правила КД. Доступность типов в фабрике XDTO, сопоставление с метаданными, поиск объектов и заполнение реквизитов обеспечиваются отдельно.

## Запуск и параметры

Скрипт находится в [kafka-tools/xdto/generator](https://github.com/ShadobaAI/kafka-tools/tree/main/xdto/generator). Интерфейс запуска сохраняет входной файл, выходной файл, пространство имён и необязательные параметры именования по адресу топика.

Команда из корня репозитория `kafka-tools`:

```powershell
python .\xdto\generator\asyncapi2xsd.py .\spec.yaml .\out.xsd -n http://example.com/xdto
```

С параметрами именования:

```powershell
python .\xdto\generator\asyncapi2xsd.py .\spec.yaml .\out.xsd -n http://example.com/xdto --prefix crm. --suffix .changed
```

| Аргумент | Обязательность | Назначение |
| --- | --- | --- |
| Входной путь | Обязателен. | YAML с разделом `components.schemas`. |
| Выходной путь | Обязателен. | XSD-файл результата. |
| `-n`, `--namespace` | Обязателен. | URI целевого пространства имён — `targetNamespace`. |
| `--prefix` | Необязателен. | Начальная часть адреса топика, удаляемая при формировании имени типа. |
| `--suffix` | Необязателен. | Конечная часть адреса топика, удаляемая при формировании имени типа. |

Префикс и суффикс применяются к адресу топика, а не к именам JSON-полей. Если именование по каналу не применяется, они не меняют имя схемы. URI собственного пакета не выводится из адреса топика или версии документа и не должен принадлежать стандартному семейству EnterpriseData.

Среда запуска — Python 3.10 или новее. Зависимости зафиксированы в [requirements.txt](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/generator/requirements.txt): PyYAML 6.0.3 и lxml 6.1.1. Проверенная среда — Python 3.12. Настройка отдельного окружения описана в [документации генератора](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/generator/README.md); `python` в командах обозначает интерпретатор этого окружения.

Поддерживаемый пример модели: [supported-example.yaml](https://github.com/ShadobaAI/kafka-tools/blob/main/xdto/generator/supported-example.yaml).

## Обработка модели

Вся реализация находится в одном файле `asyncapi2xsd.py`. Загрузка, типизированная модель, проверка ограничений, компиляция схем, выпуск XSD и CLI разделены внутри файла; CLI не содержит правил преобразования.

Скрипт последовательно читает YAML, проверяет исходные определения, разрешает ссылки и имена, строит модель типов и записывает XSD. Проверка охватывает не только синтаксис XML, но и представимость исходных требований в выбранном профиле XDTO и конвертации адаптера.

Определение общего типа не изменяется из-за ограничений одного места использования. Генератор сохраняет типизацию ссылки и не превращает любой `$ref` в ссылку на сложный тип. Порядок схем и каналов в YAML не определяет результат разрешения ссылок.

Если исходная конструкция требует неподдерживаемой модели или приводит к потере контракта, генерация завершается ошибкой. Слабее или сильнее исходного ограничения модель автоматически не подставляется.

## Именование типов

### По имени схемы

Если адрес топика не используется, основой имени типа является ключ `components.schemas`. Именование должно быть устойчивым и одинаковым во всех местах использования схемы. Читаемые подписи `title` не заменяют ключ схемы.

Нормализация имени применяется согласованно к объявлению типа и ссылкам на него. Части, разделённые точкой, дефисом или подчёркиванием, соединяются с заглавными начальными буквами: `order-details` даёт `OrderDetails`. Коллизия является ошибкой; два разных определения не объединяются автоматически. Алиас `$ref` переиспользует идентичность и имя целевого типа, а не создаёт пустой новый тип.

### По адресу топика

При наличии разрешаемой связи канала со схемой основой имени может быть адрес `channels.<канал>.address`. Из него удаляются заданные начальный префикс и конечный суффикс; оставшаяся часть преобразуется в имя типа.

| Адрес | Префикс | Суффикс | Результат |
| --- | --- | --- | --- |
| `crm.order.changed` | `crm.` | `.changed` | `Order`. |

Удаление производится на соответствующем краю адреса, а не произвольной заменой подстрок. Пустая основа имени недопустима.

Связь может проходить от сообщения канала к `components.messages` и далее через `payload.$ref` к схеме. Если подходящей связи нет, используется имя схемы. Если одна схема связана с несколькими адресами, они должны давать согласованное имя; конфликт не разрешается выбором последнего канала. При нескольких сообщениях канала учитываются их связи, а не только первое сообщение.

### Вложенные и служебные типы

Inline вложенный объект получает имя типа `{Родитель}.{Поле}`. Локальная ссылка `$ref` использует имя исходного типа; дополнительные типы с автоматически добавленным обозначением `ОбщиеСвойства` не создаются. Явно заданные имена схем сохраняются.

Имена полей XSD сохраняют соответствие ключам `properties`. Изменение имени поля JSON не является допустимым побочным результатом нормализации имени типа.

## Простые типы и UUID

| Схема YAML | Тип XSD |
| --- | --- |
| `type: string` | `xs:string`. |
| `type: string`, `format: uuid` | `tns:UUID`. |
| `type: string`, `format: date-time` | `xs:dateTime`. |
| `type: string`, `format: date` | `xs:date`. |
| `type: string`, `format: time` | `xs:time`. |
| `type: integer` | `xs:integer`. |
| `type: integer`, `format: int32` / `int64` | `xs:int` / `xs:long`. |
| `type: number` | `xs:decimal`. |
| `type: number`, `format: float` / `double` | `xs:float` / `xs:double`. |
| `type: boolean` | `xs:boolean`. |

UUID формирует собственный простой тип с именем `UUID` и ограничениями строкового представления идентификатора. Этот тип сохраняется и при переиспользовании через `$ref`. Адаптер распознаёт его ссылочную семантику по имени типа.

Обычная строка длиной 36 символов не превращается в UUID автоматически. Имя поля `id` или `ref` также не определяет тип. Типы ссылок на основе `Ref` относятся к стандартному EnterpriseData и не генерируются вместо UUID собственного формата.

Генератор определяет модель значения UUID, но не назначение ссылки и не алгоритм поиска объекта 1С. Эти сведения задаются контрактом поля и правилами конвертации.

## Объектные типы и ссылки на схемы

`type: object` формирует объектный тип с элементными свойствами по `properties`. Для содержимого используется один блок `xs:sequence`; повторяемость задаётся на отдельных элементах. Обычная модель обмена не требует смешанного текстового содержимого или преобразования полей в XML-атрибуты.

Общие объектные схемы объявляются как именованные типы и переиспользуются ссылками. Вложенная схема получает отдельный тип с устойчивым именем. Его форма и имя должны соответствовать обработке вложенных групп или составных значений в адаптере.

Локальный `$ref` разрешается в области `components.schemas` и сохраняет вид целевого определения:

- примитивная схема даёт тип значения;
- enum-схема даёт ограниченный тип значения;
- объектная схема даёт объектный тип;
- корневая схема массива создаёт объектный тип коллекции с повторяющимся свойством row; items определяет тип row, minItems/maxItems — его границы.

Ссылка на объектную схему обозначает вложенные данные, а не идентификатор связанной сущности. Неизвестные ссылки и неподдерживаемые внешние области являются ошибками. Циклические определения требуют поддержки разрешения зависимостей и конечной модели экземпляров.

## Обязательность и пустые значения

Для массивов nullable вычисляется из отсутствия поля в `required` непосредственного родителя. Если `minItems` отсутствует, используется `0`; это относится к простым спискам, массивам объектов и массивам по локальной ссылке `$ref`.

| Поле включено в `required` | `minItems` | Пустой источник |
| --- | --- | --- |
| Нет | 0 | Поле со значением `null`. |
| Нет | >0 | Nullable отключается с предупреждением; недостаточное количество элементов является ошибкой. |
| Да | 0 | Поле со значением `[]`. |
| Да | >0 | Недостаточное количество элементов является ошибкой. |

Заполненный массив проверяется по `minItems`, `maxItems` и ограничениям каждого элемента. Nullable коллекции не разрешает null её элементов. При положительном минимуме XSD не содержит nillable=true для поля массива. Предупреждение содержит категорию `[array-nullable]`, путь YAML и минимальное количество элементов.

Профиль описывает полное состояние объекта: пустые поля массива не должны пропускаться. Скрипт генерирует XSD и проверяет default/examples, но не создаёт JSON и не заполняет отсутствующие поля. Нормализация пустого источника в null или [] и обязательный выпуск поля являются требованиями к сериализации адаптера, а не автоматически реализованным поведением XSD.

В XML простой список остаётся повторяющимся элементом: minOccurs соответствует minItems, maxOccurs — maxItems либо unbounded. При minItems=0 XML допускает отсутствие элементов; nillable относится к отдельному элементу и не обеспечивает null всего списка. Для массива объектов среди нескольких реквизитов контейнер имеет minOccurs=1; количество его row определяется minItems/maxItems. Значения атрибутов, совпадающие со стандартными значениями XSD, не записываются.

Для остальных типов прежние правила сохраняются: поле вне required допускает null независимо от минимальной границы; обязательное поле с нулевой границей может быть пропущено. Отсутствующий minLength или minimum используется как 1 для расчёта присутствия, без добавления отсутствующих фасетов типа. Это правило не распространяется на minItems.


## Таблицы и списки

### Таблица объектных строк

Массив объектов в YAML представляется в XSD типом таблицы — объектом с единственным повторяющимся свойством строк. Для именованной схемы массива генератор создаёт свойство `row`, тип которого определяется `items`. YAML при этом описывает конечный массив сообщения, а не служебный контейнер XDTO.

Например:

```text
YAML: OrderLines → type: array → items: OrderLine
XSD:  OrderLines → row type="tns:OrderLine" maxOccurs="unbounded"
JSON для OrderLines: [{...}, {...}]
```

Служебное свойство `row` не входит в контракт JSON. Правила разворачивания контейнеров при отправке описаны в разделе [«Табличный объект и строка»](adapter-xdto-requirements.md#табличный-объект-и-строка).

`minItems` и `maxItems` задают границы повторяющихся строк. Отсутствующий minItems означает 0. Nullable контейнера определяется таблицей профиля: поле вне required допускает null только при нулевом минимуме. Пустая обязательная таблица с нулевым минимумом должна передаваться как [].

Массив объектов среди нескольких реквизитов допускается непосредственно в properties. Генератор создаёт таблицу `{Родитель}.{Поле}` с единственным повторяющимся полем row и inline типом строки `{Родитель}.{Поле}.Row`. Ссылка на общую схему строки переиспользует её тип. Одиночный контейнер имеет minOccurs=1; границы row определяются minItems/maxItems, nullable контейнера — таблицей профиля.

Например, обязательный `lines` с `minItems=1`, `maxItems=100` даёт обязательное одиночное свойство `lines` объектного типа таблицы, внутри которого `row` имеет границы `1..100`. Это модель XDTO для табличной части; исходный JSON сохраняет форму `lines: [{...}]`. JSON-примеры проверяются по семантической модели без создания XML-обёртки. Сам скрипт не выполняет конвертацию рабочих сообщений.

Если YAML явно описывает объект с единственным свойством-массивом объектных строк, генератор считает его уже заданной таблицей: сохраняет имя свойства строк и не создаёт дополнительный контейнер. Такой ввод позволяет описать модель XDTO, но не соответствует конечному контракту JSON адаптера: при отправке контейнер также разворачивается в массив. Для контракта сообщения используйте схему массива согласно [требованиям к YAML](yaml-requirements-for-xdto.md#таблица-объектных-строк). Добавление второго свойства меняет классификацию типа: он перестаёт быть табличным контейнером.

### Простые списки

Массив простых значений создаёт непосредственно повторяющееся свойство простого типа без табличной обёртки. Ограничения items, включая enum и локальную ссылку на простой тип, применяются к каждому элементу. При отсутствии minItems нижняя граница равна 0. Nullable разрешён только для поля вне required с нулевым минимумом. Например, fixedTags с minItems=1/maxItems=3 имеет границы 1..3 и не допускает null.

Количество элементов списка проверяется по minItems/maxItems. Пустой источник обрабатывается по таблице профиля; обязательное поле с нулевым минимумом должно присутствовать в JSON как []. Отсутствующий minItems означает 0.

Для прямого повторяющегося свойства отдельного XML-элемента пустого массива нет. Отсутствие и присутствующий пустой простой массив неразличимы в повторяющихся XML-элементах. При maxItems=1 генератор сохраняет признак списка для проверки JSON-примеров и границу 1 в XSD; это не скалярная схема items.

### Самостоятельные строки и пакеты

Самостоятельная строка табличной части описывается отдельным объектным типом с контекстом владельца и идентификацией строки. Генератор создаёт модель этого объекта, но не регистрацию изменений строки или правила обновления владельца.

Корневые массивы и пакеты записей рассматриваются только в рамках определённого сценария адаптера. Наличие схемы массива не означает автоматическую поддержку любого пакетного протокола.

## Перечисления и ограничения

`enum` создаёт ограниченный простой тип с сохранением базового типа и кодов. Поддерживаются общие схемы и поля, в том числе поля объектной строки таблицы. Boolean enum и enum для UUID отклоняются. Подписи `x-enumNames` не заменяют коды и не становятся значениями перечисления XSD.

Ограничения строк и чисел сохраняются соответствующими фасетами, если их смысл точно представим. Проверяются согласованность границ, совместимость с типом и соответствие значения по умолчанию ограничениям.

Переносимый профиль `pattern` включает ASCII-литералы, положительные ASCII-классы и диапазоны, `\d`, экранированные специальные символы и обычные повторения. Поиск подстроки преобразуется в соответствующий XSD-шаблон, включая текст до и после совпадения. Wildcard `.`, группы, альтернативы, lookaround, backreference и ленивые повторения отклоняются. Различия целевого диалекта описаны в [XML Schema Datatypes](https://www.w3.org/TR/xmlschema-2/#regexs).

`multipleOf` сохраняется только точным способом. Ограничение дробных знаков может описывать шаг `0.01` для десятичного значения, но не заменяет шаг `0.05`. Непредставимое ограничение не удаляется и не подменяется более слабым.

Неизвестный существенный `format`, несовместимое ограничение или неподдерживаемый вид enum вызывает явную ошибку.

## Аннотации и расширения

`xs:documentation` содержит `title`; если он отсутствует или пуст после удаления пробелов, используется `description`. Пробелы в начале и конце удаляются, переносы строк и последовательности пробелов сворачиваются в один пробел. `deprecated` и описательные `x-*` не создают элементы XSD и не меняют ограничения. Поля данных возникают только из `properties`.

`x-enumNames` и `x-topics` являются рекомендуемыми необязательными аннотациями. `x-last-modified` может описывать изменение спецификации. Отсутствие этих расширений не препятствует генерации; их наличие не создаёт правила КД, связи объектов или дополнительные свойства сообщения.

Машинное расширение генератора требует отдельного документированного значения. Неизвестному `x-*` автоматически не приписывается команда изменения модели.

## Поддерживаемый профиль и ошибки

Базовый профиль ограничен конструкциями, определёнными в [требованиях к YAML](yaml-requirements-for-xdto.md). Композиция `allOf`, альтернативы `oneOf` и `anyOf`, явный `null`, открытые словари и другие расширенные конструкции требуют отдельных правил преобразования. Их корректность в AsyncAPI не означает включение в базовый профиль.

`additionalProperties=true`, `additionalProperties` со схемой и `patternProperties`, `AdditionalInfo`, неизвестные проверочные ключи и структурные ограничения рядом с `$ref` отклоняются. Модель переносит объявленные `properties`; отсутствие `additionalProperties` не выдаётся за явный запрет неизвестных полей исходной JSON Schema. Полная эквивалентность произвольной JSON Schema и XSD не заявляется.

Вход ограничен 10 MiB, 100 000 узлами и глубиной 128; раскрытие ссылок — 100 вложенными определениями. Regex ограничен 4096 символами и явными границами повторения до 1000. Числовая запись ограничена 1000 цифрами и модулем десятичного показателя до 1000; фактическая представимость дополнительно проверяется libxml. Дубли YAML, merge и рекурсивные YAML-структуры вызывают ошибку.

Ошибка должна указывать проблемную схему или поле, путь в YAML и причину: неразрешённую ссылку, конфликт имени, противоречие ограничений, неподдерживаемую конструкцию либо невозможность сохранить форму данных.

Схема компилируется через `lxml.etree.XMLSchema`, значения default/examples и коды enum проверяются до записи. Новый файл создаётся временно в выходном каталоге и атомарно заменяет результат; при ошибке прежний файл сохраняется. Входной и выходной пути должны различаться. Успех имеет код завершения `0`, ошибка входа или файловой системы — `2` и диагностику в stderr. Имена общих типов сортируются устойчиво; порядок полей исходного объекта сохраняется.

## Импорт и использование XDTO-пакета

Результирующая схема содержит `targetNamespace`, объявления пространств имён `xs` и `tns`, `elementFormDefault="qualified"` и `attributeFormDefault="unqualified"`. `tns` обозначает собственное целевое пространство имён и не является частью имени типа.

XSD импортируется средствами EDT или Конфигуратора в XDTO-пакет. Типы и зависимости должны быть доступны глобальной фабрике XDTO конфигурации. В настройках конвертации адаптера URI пакета указывается как формат сериализации или десериализации; ПОД и правила КД выбираются отдельно.

Импорт подтверждает доступность модели в 1С, но не корректность бизнес-сопоставлений. Использование пакета требует согласования правил и примеров обмена в нужных направлениях. Описание модели XDTO и проверка конвертации приведены на связанных страницах.

## Массивы, группы и аннотации формата

Корневой массив и общая схема массива по $ref создают объектный тип коллекции с повторяющимся полем `row`. Исходное значение в YAML default/examples остаётся списком; при проверке оно переводится в XML коллекции. Скалярное поле, ссылающееся на такую схему, также принимает список. Границы 0 и 1 поддерживаются; неизвестные поля в примерах объектов отклоняются.

Начальный `^` и конечный `$` в pattern переводятся в ограничения начала и конца строки, сохраняя семантику поиска при отсутствии якорей. Конечный `$` требует конца входной строки, без режима multiline; завершающий перевод строки не игнорируется. Семантика якорей соответствует [ECMAScript CompileAssertion](https://tc39.es/ecma262/2024/multipage/text-processing.html#sec-compileassertion). Остальные ограничения переносимого regex-профиля сохраняются.

`format: email` поддерживается как [аннотация формата JSON Schema](https://json-schema.org/draft/2020-12/json-schema-validation#name-format-annotation-vocabular) строки и сохраняется в xs:documentation. Он не превращается в приближённый regex или неизвестный тип. minLength/maxLength/pattern и enum строки проверяются; полная проверка адреса электронной почты форматом email в XSD не выполняется. Неизвестные форматы продолжают вызывать ошибку.

### Запись значений по умолчанию XSD

Атрибут не записывается, если его вычисленное значение совпадает со стандартным значением XSD: minOccurs=1, maxOccurs=1, nillable=false, attributeFormDefault=unqualified. Отличающиеся значения сохраняются явно, например minOccurs=0, maxOccurs=unbounded, nillable=true и elementFormDefault=qualified. Это сокращение записи не меняет модель; сначала вычисляются свойства с приоритетами исходного YAML, затем сравниваются со значениями по умолчанию целевого XSD.
