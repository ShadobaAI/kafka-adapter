# Производительность

Начните с измерения очередей и пропускной способности. Пропускная способность зависит от частоты и размера сообщений, кода обработчиков, нагрузки на СУБД и параметров Kafka.

## Как найти узкое место { #bottleneck }

| Сигнал | Какой этап проверить |
|---|---|
| Запись объекта замедлилась при включённой регистрации | Запись в БД и подписку регистрации. |
| Исходящие копятся в **Новое** | Сериализацию и запросы обработчика продюсера. |
| Исходящие копятся в **Обработано** | Отправку, сеть и время подтверждений Kafka. |
| У группы растёт отставание, входящая очередь мала | Чтение Kafka и число разделов, назначенных группе. |
| Сообщения загружаются, но входящие **Новое** накапливаются | Десериализацию, прикладные записи и задержки повторов. |

Подбирайте число **Подпотоков обработки** отдельно от **Подпотоков транспорта**. Изменяйте один параметр за замер, затем [перезапускайте потоки](../configuration/jobs.md#settings-restart). Для уменьшения пауз между порциями проверьте эффект [потокового режима](../configuration/jobs.md#streaming-mode).

## Дополнительные индексы { #additional-indexes }

Дополнительные индексы очередей задаются в метаданных. Для MS SQL Server администратор СУБД может использовать приведённый код, чтобы получить DDL для фактических таблиц и колонок. Перед применением сравните DDL с уже существующими индексами. Выполните код на сервере 1С, скопируйте значение переменной `ТекстSQL` и выполните полученный SQL вручную в базе данных информационной базы.

```bsl
ТекстSQL = "";

Регистры = Новый Массив;
Регистры.Добавить(Метаданные.РегистрыСведений.кфкИсходящиеСообщения);
Регистры.Добавить(Метаданные.РегистрыСведений.кфкВходящиеСообщения);
Для Каждого Таблица Из ПолучитьСтруктуруХраненияБазыДанных(Регистры, Истина) Цикл

    ОбъектМетаданных = ОбщегоНазначения.ОбъектМетаданныхПоПолномуИмени(Таблица.Метаданные);
	Для Каждого Индекс Из ОбъектМетаданных.ДополнительныеИндексы Цикл

		ПоляSQL = Новый Массив;

		Для НомерГруппы = 0 По 1 Цикл
			ИменаПолей = Новый Массив;
			Группа = ?(НомерГруппы = 0, Индекс.ИндексируемыеПоля, Индекс.ДополнительныеПоля);

			Для Каждого Поле Из Группа Цикл
				ИмяПоляХранения = Таблица.Поля.Найти(Поле.Имя, "ИмяПоля").ИмяПоляХранения;
				ИменаПолей.Добавить("[" + СтрЗаменить(ИмяПоляХранения, "]", "]]") + "]");
			КонецЦикла;

			ПоляSQL.Добавить(СтрСоединить(ИменаПолей, ", "));
		КонецЦикла;

		ТекстSQL = ТекстSQL + СтрШаблон("CREATE NONCLUSTERED INDEX [IX_кфк_%1] ON [dbo].[%2] (%3)",
			СтрЗаменить(Индекс.Имя, "]", "]]"),
			СтрЗаменить(Таблица.ИмяТаблицыХранения, "]", "]]"),
			ПоляSQL[0]);

		Если Не ПустаяСтрока(ПоляSQL[1]) Тогда
			ТекстSQL = ТекстSQL + " INCLUDE (" + ПоляSQL[1] + ")";
		КонецЕсли;

		ТекстSQL = ТекстSQL + ";" + Символы.ПС;

	КонецЦикла;

КонецЦикла
```

## Точки измерения { #measurements }

Сравнивайте одни и те же показатели до и после изменения:

1. **Лаг регистрации** — интервал между изменением объекта и появлением записи в очереди.
2. **Лаг отправки** — время от записи в очередь до статуса «Выгружено».
3. **Лаг доставки в потребителя** — end-to-end: от записи в 1С-отправителе до записи в 1С-получателе.
4. **Throughput** — сообщений/сек по топику (брать из кода мониторинга Kafka или из `кфкИсходящиеСообщения` за период).

Дашборды — через [внешнее логирование](../configuration/logging.md), совместимый HTTP-приёмник и настроенное внешнее хранилище. Базовые запросы — [мониторинг](monitoring.md#monitoring-queries).

## Как провести замер у себя

Чтобы решения о тюнинге опирались на данные, а не на ощущения, зафиксируйте профиль и измерьте базовую линию до изменения параметров:

1. **Профиль нагрузки** — типичный размер тела сообщения, частота регистрации (сообщений/мин), число партиций топика и replication factor.
2. **Базовая линия** — лаги и throughput из раздела [Точки измерения](#measurements) при текущих настройках, на интервале, который покрывает типичные пики обмена.
3. **Изменение одного параметра** — меняйте по одному рычагу за итерацию (подпотоки обработки → подпотоки транспорта → потоковый режим) и сравнивайте с базовой линией.
4. **Контроль стоимости** — вместе с лагами следите за CPU/RAM сервера 1С и числом фоновых заданий: рост параллелизма не бесплатен.

## Типовые проблемы производительности

- [Очередь постоянно растёт](troubleshooting.md#growing-queue).
- Медленная сериализация в обработчике продюсера — профилировать и выносить тяжёлые выборки за пределы обработчика.
- При блокировках регистра исходящих проверьте планы запросов, актуальность индексов и перекрытие операций с очередью.
