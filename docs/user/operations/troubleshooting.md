# Типовые проблемы

## Сообщения застряли в статусе «Новое» { #new-messages-stuck }

1. Убедитесь, что подсистема включена, обмен разблокирован и [регламентное задание](../configuration/jobs.md#scheduled-job) выполняется.
2. Для исходящей записи проверьте блокировку сериализации у продюсера и правило для типа объекта. Для входящей — блокировку десериализации и правило для топика.
3. Для входящей записи проверьте поле **Задержка, с**. После [отложенного повтора](../development/consumer-handler.md#deferred-retry) статус остаётся **Новое** до следующей попытки.

## Статус «Ошибка выгрузки» { #send-error }

Прочитайте **Текст журнала** в исходящей записи. Проверьте сетевую доступность узлов с сервера 1С, конфигурацию SASL/TLS и [логи компоненты](../configuration/logging.md#connector-logging). Проверка TCP показывает доступность порта. Для проверки прав и аутентификации выполните нужную операцию Kafka с параметрами подключения адаптера.

Фоновый повтор ограничен тремя попытками, включая первоначальную. После устранения причины воспользуйтесь командой **Вернуть в очередь**. [Статусы и повторы](statuses.md#automatic-retry)

## Kafka сообщает «Topic authorization failed» { #topic-authorization }

1. Сверьте кластер и точное имя топика с настройками продюсера или консьюмера.
2. Проверьте права учётной записи адаптера на операцию с топиком. Для чтения также могут потребоваться права на группу консьюмеров.
3. Если меняли параметры подключения, дождитесь [применения настроек](../configuration/jobs.md#settings-restart).
4. После исправления проверьте обмен тестовым сообщением и разберите ошибочные записи очереди.

Список операций и ресурсов описан в [документации Kafka по ACL](https://kafka.apache.org/42/security/authorization-and-acls/).

## Статус «Ошибка обработки» { #processing-error }

Откройте журнал записи. Проверьте, выбрано ли правило сериализации или десериализации, заполнено ли имя метода и соответствует ли тело сообщения контракту. Сообщения «Время ожидания превышает 5 минут.» и «Исчерпан лимит повторов.» относятся к [лимитам отложенного повтора](../development/consumer-handler.md#deferred-retry).

После исправления воспользуйтесь [командой повтора](statuses.md#manual-actions). Записи в этом статусе требуют ручного запуска или возврата в очередь.

## Фоновые задания не запускаются { #jobs-do-not-start }

Проверьте состояние задания, пользователя обмена и блокировку на вкладке **Фоновые задания**. После переноса или копирования базы проверьте ограничения БСП на работу с внешними ресурсами. Затем откройте журнал регистрации 1С и изучите ошибку задания. [Условия запуска](../configuration/jobs.md#scheduled-job)

## Очередь постоянно растёт { #growing-queue }

Посчитайте записи по статусам несколько раз за один интервал нагрузки. Для исходящих отличите накопление **Новых** записей от накопления **Обработанных**, готовых к выгрузке. Для входящих проверьте и отставание группы Kafka, и локальную очередь. Меняйте параллельность только на этапе с отставанием. [Точки измерения](performance.md#measurements)

## Входящие сообщения не поступают { #no-incoming-messages }

Проверьте блокировку чтения у брокера и консьюмера, имя топика, идентификатор группы и её смещения. Разные участники одной группы могут читать разные разделы. Если группа новая, проверьте `auto.offset.reset`. [Настройка группы](../configuration/consumers.md#consumer-groups)

## Сообщения уходят в очередь по кругу { #exchange-loop }

Если запись данных из Kafka порождает исходящую регистрацию того же объекта, вызовите `кфкИнтеграция.Отключить(Объект)` перед `Записать()` в обработчике консьюмера. [Пример записи](../examples/incoming-catalog.md)

## При записи объекта возникла ошибка регистрации { #registration-error }

Проверьте подробности события `Адаптер Kafka.Регистрация при записи`. После исправления причины зарегистрируйте нужный объект повторно. [Диагностика регистрации](diagnostics.md#registration-event)
